# Security Policy

VEdge is a password manager, so a security bug here can cost someone every credential they own.
Reports are genuinely welcome — including ones that turn out to be wrong.

## Supported versions

VEdge is a solo, open-source project. Fixes land on the **latest release**; there are no backports to
older versions.

| Version | Supported |
| --- | --- |
| 1.0.x | ✅ |
| < 1.0 | ❌ (pre-release; no public builds existed) |

## Reporting a vulnerability

🔴 **Please do not open a public issue for a security bug.** A public report on a password manager
publishes a working attack to everyone — including attackers — before a fix exists.

Instead use **[private vulnerability reporting](https://github.com/vyngt/vedge/security/advisories/new)**
(GitHub → the repo's **Security** tab → *Report a vulnerability*). It's private between you and the
maintainer, and needs no email address from either of us.

Helpful to include, as far as you can get:

- What the impact is — what an attacker ends up able to read, change, or bypass.
- Steps to reproduce, or a proof of concept.
- The VEdge version (**Settings ▸ About**) and your Windows version.
- Whether it needs an unlocked vault, physical access, or prior code execution.

**What to expect.** This is a hobby project maintained by one person, so: acknowledgement within
**7 days**, best effort after that. You'll be told whether it's accepted, and credited in the advisory
and release notes when a fix ships — unless you'd rather stay anonymous. If a report is out of scope,
you'll get a reason, not silence.

## What VEdge is designed to protect

The core threat VEdge defends against is **an attacker who obtains your vault files** — a stolen
laptop, a backup copied off a synced folder, a disk pulled from a dead machine.

Against that attacker:

- Unlocking needs **two** secrets: your master password *and* a 16-byte device **Secret Key**, so a
  guessed or leaked password alone is not enough.
- They're combined (HKDF-SHA256) and stretched with **Argon2id (256 MiB, t=3, p=4)**.
- Every entry gets a **fresh data key on every write**, wrapped with AES-KW and sealed with
  **XChaCha20-Poly1305**, bound to the entry's id and version.
- Decrypted secrets never cross into the UI layer unless you explicitly copy or reveal one — and
  that action is written to the audit log.

Reports that weaken any of the above are **in scope**, as are: breaking the capability/CSP
containment, escaping the WASM-secret boundary, key material surviving in memory or landing on disk
in the clear, and flaws in backup/restore, export/import, or the credential operations
(change-password, rotate, Recovery Key, re-key).

## Out of scope

These aren't things VEdge claims to survive:

- **A compromised operating system** — malware, a keylogger, or a debugger attached to the process.
  Nothing a user-space password manager does survives an attacker already running as you.
- **Physical access to an unlocked, running session.**
- **Screen capture / screenshots** of revealed secrets. Screen-capture protection is a deliberate
  post-1.0 item.
- **Losing your keys.** A forgotten master password with no Recovery Key, or a lost Emergency Kit, is
  unrecoverable *by design* — that's the trade for having no server able to reset it.
- **Attacks that already assume both the master password and the Secret Key.**
- Social engineering, phishing, or physical coercion.
- Reports generated by a scanner with no demonstrated impact on VEdge specifically.

## Known and deliberate trade-offs

These are decided, documented, and **not** bugs. A report arguing the *reasoning* is wrong is
welcome; a report that simply notes the fact is not a finding.

- **The installer is unsigned.** No code-signing certificate for 1.0, so Windows SmartScreen warns on
  first run. The published **SHA-256 checksums** are the integrity story — verify before installing.
- **There is no auto-update**, only a manual check. An updater is a standing remote-code-execution
  channel into a process holding every user's vault keys, and its signing key would become the
  project's highest-stakes secret; with the certificate deferred it would also auto-install *unsigned*
  binaries.
- **`withGlobalTauri` is `true`.** The frontend genuinely uses `window.__TAURI__`. Containment is the
  curated capability set (8 grants) plus a real CSP — both pinned by a test so they can't silently
  widen.
- **The database file is plain SQLite**, not SQLCipher. Encryption is per-entry at the application
  layer: the file holds only ciphertext columns. This is a design choice, not an oversight.
- **Snapshots live inside the vault folder** and are not backups — they don't survive losing the disk.
- **Re-key protects forward and cannot un-leak the past.** If a copy was taken while an attacker also
  had your credentials, re-keying stops future opens of that copy; it can't retract what was read.
- **MIT-licensed**, which permits closed-source forks. Accepted deliberately.

One real limitation worth naming rather than hiding: **KDF parameters are stored in the vault and
trusted at unlock** (they have to be — they're needed to re-derive the key), and there is no minimum
floor. A vault created by a build with weakened parameters keeps them. In practice this only affects
test-created vaults, but a hardening pass is a fair thing to suggest.

## Disclosure

Coordinated disclosure. Once a fix is released, the advisory is published with credit to the reporter.
If a report is still unfixed after **90 days**, you're free to disclose it publicly — a slow
maintainer shouldn't be able to silence a real finding indefinitely.
