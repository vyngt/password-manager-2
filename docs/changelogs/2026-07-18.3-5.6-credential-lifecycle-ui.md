# Slice 5.6 — Credential Lifecycle UI (2026-07-18)

**You could create, delete, snapshot, back up and export a vault — but you could not change its master
password or rotate its Secret Key from the UI.** The backend has been able to since Phase 3
(`change_password` is implemented, registered, tested, atomic, and takes `new_password` **and**
`Option<new_secret_key>`); nothing reached it. 5.6.0 spent a whole slice making that button *safe* (tags now
survive a KEK change). This slice is the button — plus two long-owed non-UI corrections.

## ① The "recovery" vocabulary rename — Full/core, so it means exactly one thing

5.1 shipped a **Secret-Key-unlock** surface misnamed "recovery"; 5.7 will introduce a *genuine* Recovery
Key. Two credentials both called "recovery" is a guaranteed bug, so the misnamed surface is renamed end to
end **before** 5.7 is specced in code. Scope was confirmed as **Full/core** (not just the IPC surface):

- **IPC:** `RecoveryOutcomeDto`→`SecretKeyUnlockOutcomeDto`, `UnlockWithRecoveryKeyInputDto`→
  `UnlockWithSecretKeyInputDto`, wire field `recovery_key_display`→`secret_key_display`.
- **Tauri:** command `unlock_with_recovery_key`→`unlock_with_secret_key`, module `commands::recovery`→
  `commands::secret_key`, mapper `recovery_outcome_to_dto`→`secret_key_unlock_outcome_to_dto`.
- **App:** `api::recovery`→`api::secret_key` (+ the wire string), UI signals/handlers/test-ids
  (`recovery-key`→`secret-key`, `recovery-submit`→`secret-key-submit`), `unlock.recovery_*`→
  `unlock.secret_key_*` locale keys.
- **Core:** use case `recover_vault`→`unlock_with_secret_key` (parallels `unlock_vault`),
  `RecoverVaultInput`/`RecoveryOutcome`, domain module `domain::vault::recovery`→`secret_key`,
  `RECOVERY_FORMAT_PREFIX`→`SECRET_KEY_FORMAT_PREFIX`, `VaultError::InvalidRecoveryKey`→`InvalidSecretKey`
  (the wire error *kind* stays `"Invalid"`), `tests/recover_vault.rs`→`tests/unlock_with_secret_key.rs`.

🔴 **KEPT (do NOT rename):** `AuditAction::RecoveryUsed` — its variant string is **persisted** in shipped
audit logs (renaming it is a data migration for cosmetics; "recovery" there legitimately means "recovered
access via the Secret Key"). Its emitter stays put inside the renamed use case. The Login **"recovery
codes"** 2FA feature is a false-positive of the word — untouched. Pure mechanical rename, **no behaviour
change** — host stayed at **851** for the rename commit; the 5.1 e2e + the core/domain tests pass *renamed,
not rewritten*.

## ④ Current-password verification — an extraction, not a fourth KDF copy

The spec requires verifying the current password **before** the O(n) rewrap (an unlocked, unattended vault
is exactly what a re-auth defends). That verify already lived inside `enroll_biometric`. Rather than write a
fourth copy of the KDF chain, it was **extracted** into a shared core use case
**`reauthenticate_master_password(session, kdf, keychain, password) -> Zeroizing<KEK>`**: resolve the
current Secret Key from the keychain → one Argon2 pass → constant-time `verify_hash` compare →
`WrongCredentials` on mismatch, returning the re-derived KEK. `enroll_biometric` now calls it (pure
extraction — the 7 existing biometric tests pass unchanged) and uses the returned KEK for its store; the
credential flows call it and discard the KEK. **Documented constraint (no new edge):** it needs the current
Secret Key on-device, the *same* precondition `enroll_biometric` already carried.

## ② Change master password

`ChangePasswordInputDto` gains `current_password`; the `change_password` command re-authenticates it (via
the extraction) **before** `change_password_core`, so a wrong password returns `WrongCredentials` and
mutates nothing — no brick. On success the session stays live. The UI is a Settings ▸ Security row + dialog
(`change_password_setting.rs`): current password → new password + `PasswordStrengthMeter` (reused
`password_score`, `MIN_STRENGTH = 2`) → confirm; a `busy` signal gates the dialog against a double-submit
(two overlapping rewraps are undefined). The app-side `api::password` module is unparked (its module-level
`#[allow(dead_code)]` dropped).

## ③ Rotate Secret Key — and the reversed "orphaned kit" copy

A new `rotate_secret_key` command generates a fresh key **server-side** (the CSPRNG stays in core), rotates
to it via `change_password` (keeping the master password), and returns only the formatted `secret_key_display`
— the **same show-once contract as `create_vault`**; the raw key never crosses to WASM (consistent with the
5.4 sentinel, which seals *stored* secrets). The UI (`rotate_secret_key_setting.rs`) is a two-phase dialog:
phase 1 re-auths + rotates, phase 2 shows the new key (`SecretDisplay`) and re-issues the Emergency Kit
(the reused `write_pdf` save-flow, which reads the freshly-written keychain).

🔴 **The reversed copy.** The plan long said a rotation *"orphans every previously-printed kit."* It
**doesn't** — the old kit is the ONLY key to every `.vbk` and snapshot taken *before* the rotation. The
dialog now says: *"Rotating your Secret Key changes what unlocks this vault going forward. **Keep your old
Emergency Kit** — it's the only key to the backups and snapshots you made before now. VEdge will issue a new
kit for this vault."* Telling the user to shred it would have destroyed their backups.

## DRIFTs (documented)

1. **Rename scope = Full/core** (chosen with the user over IPC-surface-only) — the acceptance criterion
   "recovery means exactly ONE thing" and removing the 5.7 collision at its source both required core.
2. **The "tagged vault survives" guarantee is proven at the host level** (`tests/tag_keys.rs`), **not in the
   e2e** — the UI has no simple tag-creation path (tags are created via import or bulk-applied from an
   existing set), and the DEK rewrap is identical with or without a tag. The e2e proves a seeded *entry*
   survives the rewrap through the UI.
3. **The rotate command has no host coverage** (only the on-device e2e) — the codebase tests command *inner
   helpers*, not the `#[tauri::command]` wrappers (which take a hard-to-construct `tauri::State`). Its
   constituent pieces (`change_password`, `generate_secret_key`, `format_secret_key`,
   `reauthenticate_master_password`) are all host-tested; only the thin wiring is e2e-only.
4. **Keychain-less edge:** a biometric-only vault whose keychain lacks the Secret Key cannot re-authorize
   here (the same precondition `enroll_biometric` has); the dialogs show the pointed "restore via your
   Emergency Kit" message (an `ApiError::Keychain` arm, from the `/code-review high` pass).
