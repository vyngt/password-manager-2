# Slice 5.3.1c — Selection + the action bar

Third PR of slice 5.3.1 (Vault Page & Entry Selection). PRs `a` (DataTable hardened, #64) and `b` (the
table migration, #65) landed the machinery; this wires **multi-select + the bulk action bar** onto it and
lands the slice's **two data-loss guards**. Spec:
`.../Phase 5 - Data Safety & Recovery/Specs/5.3.1 - Vault Page & Entry Selection` (④/⑤/⑥).

## What shipped

### The two data-loss guards — pure, host-tested, written first

New `features/vault/selection.rs` holds the guards as pure functions so they were locked **before** any UI
wiring:

- 🔴 **④ Select-all is filtered-scoped, never the whole vault.** The header checkbox / Ctrl+A select
  exactly the rows `filter_and_sort` yields (`DataTable` only ever sees the `visible` keys), so the scope
  *cannot* exceed the filter — architecturally, not by convention. A host test builds 247 entries, filters
  to 12, and asserts select-all is those 12 (not 247). *(Filter to 12 → select-all → Trash must not wipe the
  vault.)*
- 🔴 **⑤ A filter/search/scope/source change clears the selection; a sort change does not.** `ViewIdentity
  { filters, trashed_view }` **deliberately omits `SortKey`**, so a page `Memo<ViewIdentity>` never reads
  `sort` and the clear `Effect` can't even re-run on a re-sort — the selection survives a re-sort (⓪),
  structurally. Host tests pin each direction (facet/scope/trash change ⇒ clear; sort-only ⇒ keep).

### Selection wired through `VaultTable` → `DataTable`

`DataTable`'s selection API (built in `a`) was unused by the vault; `VaultTable` now forwards it:
`selectable`, `selected_rows`, `on_selection_change`, plus localized `select_all` / `deselect_all` /
per-row `select` aria labels (the per-row one pre-resolved into the `VaultRow` view-model, since the
`Send + Sync` `row_select_label` closure can't call `t_string!`). The page owns
`selected: RwSignal<Vec<String>>` (entry ULIDs — ⓪), passes `selectable = !trashed_view` (a **mount-time
snapshot**: `DataTable::selectable` is a static bool, and the page already remounts `VaultTable` on every
active/trash switch via its `loading` `<Show>`), and clears it from the ⑤ `Effect`. Because `on_row_click`
is set, a **plain row click opens the detail drawer** while the **checkbox / shift-click / Ctrl+A / Space**
select — "click = open, check = select".

### The action bar (⑥) — a mode, not a strip

At N>0 the toolbar **is replaced** by `SelectionBar` (`role="toolbar"`, `aria-live="polite"` count, `Esc`
clears): **N selected · Tag · Move · Trash · ✕**. Verbs reuse the single-entry operations (there are no
bulk commands — 3.5's "bulk" was *generate-secrets*), looping sequentially with stop-on-error, then clearing
the selection and refreshing (the `on_empty` / `on_empty_trash` precedent). Each handler restricts the
selection to ids **still present** in the active list, so a stale id (an entry deleted single-handedly since
selecting) is dropped, never acted on.

- **Trash** → a confirm (`BulkTrashDialog`) then a `soft_delete_entry` loop. Soft-delete is reversible, but
  a destructive verb on a *set* is higher-stakes than the single-row action, so it confirms.
- **Move** → `SelectionMoveDialog` (reuses `flatten_tree` + the `Select` folder picker) then a `move_entry`
  loop to one destination (or root).
- **Tag** → `SelectionTagDialog`, an **add-only** chip picker; the page unions the chosen tags into each
  entry's existing `tag_ids` (`set_tags` *replaces*, so it must union) via `union_tags`. Add-only because
  removing a tag across a heterogeneous selection is ambiguous.

## Decisions / deviations

- **Export… + the whole-vault "Select all N →" escalation are NOT here** — they land in PR `d` with the
  three-scope export dialog and the `Option<Vec<EntryId>>` scope plumbed through core→tauri→api (absent
  today). Deferring them keeps the selection **⊆ the filter**, which is exactly what makes ⑤ safe.
- **Multi-select is active-view only** (`selectable = !trashed_view`). Trash-view bulk (Restore /
  Delete-permanently N) would need a second bar variant; deferred. The single-row Restore/Delete +
  Empty-trash stay.
- **Success toasts are count-free** ("Moved the selected entries to Trash.") — `t_string!` interpolation
  needs the `interpolate_display` feature (not enabled project-wide), and enabling it for a toast count
  isn't worth the blast radius. The **count stays in the confirm dialog titles/messages** (which use `t!`,
  the view-context macro) and in the bar's live count.
- `Filters` gained `Debug, PartialEq, Eq` (it holds only facets/search, no secrets) so `ViewIdentity` can
  compare. `filter_and_sort` is **unchanged**.

## Fix: restore drag-entry-to-folder (regression from PR `b`)

The pre-DataTable entries table had `draggable="true"` on **every** row and wrote the entry id to
`dataTransfer` on dragstart, so an entry could be dragged onto a **folder tree** node in any sort. The `b`
migration gated `DataTable`'s `draggable` (and its dragstart) on `reorder_enabled` (Manual sort only) — which
also silently killed **drag-to-folder** in the default (NameAsc) view, mis-described in `b`'s changelog as an
improvement. Fixed here: `DataTable` gained a `row_draggable` prop (draggability for an **external** drop
target, independent of `reorder_enabled`; dragstart writes the `row_key` to `text/plain`). `VaultTable` passes
`row_draggable=Signal::stored(true)`, restoring the old always-draggable behavior — drag-to-folder works in
every sort again, while row-to-row **reorder** stays Manual-only. *(No automated drag e2e exists — covered by
the manual smoke.)*
