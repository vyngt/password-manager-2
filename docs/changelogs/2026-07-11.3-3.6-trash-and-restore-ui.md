# Slice 3.6 — Trash & Restore UI

Gives the read-only Trash view its verbs — **Restore**, **Delete permanently**, **Empty trash** — and,
per a mid-slice product call, **reworks the entry point: Trash is now a folder in the left sidebar**
(Finder / email style) instead of a filter `Select`. UI-only in `vedge-app` — the core use-cases + Tauri
commands + `api::entry` wrappers were already wired. Spec:
`.../Phase 3 - Password Generator/Specs/3.6 - Trash and Restore UI`.

**The hard rule (blob-leak caveat):** permanent deletion routes through `hard_delete_entry`, never
`soft_delete_entry` — only `hard_delete_entry` purges the Document `{stem}.vedge_blobs/{id}.blob` sidecar
(+ version history + a `PermanentlyDeleted` audit). Permanent-delete and Empty-trash both use it.

## What shipped

### Trash as a sidebar folder (replaces the filter Select)
- Dropped the "Active / Trash" `Select` from the toolbar (`vault_filters.rs` + its `trashed_view` prop).
- Added a **Trash `SidebarItem`** at the bottom of `FolderTree` (separator above, trash-can icon), driven
  by a new `trashed_view: RwSignal<bool>` prop — `selected` when trash is the view, click enters it.
- **All / Unfiled / Trash stay always-visible** (the navigation); the **folder rows + new-folder chrome
  hide in trash** (`<Show when=!trashed_view>`). This is load-bearing, not cosmetic: the folder tree is
  built from the loaded entry list, which is the *trashed* set in trash view — showing the user folders
  would render folders derived from trashed data. All/Unfiled `selected` gain `&& !trashed_view` (so only
  Trash highlights in trash), their badges blank in trash, and their click clears `trashed_view` (leaving trash).
- The scope-reset `Effect` now fires **only on entering** trash (false→true) — else clicking **Unfiled**
  *from* trash would be clobbered back to All. Smart folders stay visible in trash (their content isn't
  items-derived; clicking one navigates back to active). The folder breadcrumb stays hidden in trash.

### Actions — rows, detail, header
- **Rows** (`vault_table.rs`): the action-cell `<Show when=!hide_delete>` gains a **fallback trash cluster**
  — Restore (`FaTrashArrowUpSolid`) + Delete-permanently (`FaTrashCanSolid`, Danger), both
  `stop_propagation` before firing. New `on_restore: Callback<String>` / `on_hard_delete: Callback<IndexEntryDto>` props.
- **Detail** (`vault_detail.rs`): a trashed entry becomes a **read-only tombstone** — Restore +
  Delete-permanently replace copy/move/edit/export (via `Either`), and favorite / history / tag-assign are
  hidden. This **closes the detail half of ticket #4** (a trashed entry could still be copied/edited) → 3.7 drops it.
- **Header** (`vault.rs`): an **Empty trash** Danger `Button`, shown only in trash view when the list is
  non-empty (an empty list shows the "Trash is empty" state instead).

### Confirms + handlers
- New `features/vault/trash_confirm.rs` (mirrors `folder_delete.rs`): `PermanentDeleteDialog` (names the
  entry) + `EmptyTrashDialog` (interpolates the count). Restore is non-destructive → **no** dialog.
- `vault.rs` handlers (all `spawn_local`, toast + `refresh()`): `on_restore` (direct `restore_entry`),
  `on_hard_delete` (opens the confirm), the confirm's `hard_delete_entry`, and `on_empty_trash` (loops
  `hard_delete_entry` over every trashed id — mirrors the folder `on_empty`; stop-on-first-error). Each
  clears the selection if the acted-on entry was open, so the detail closes.
- Removed the two `#[allow(dead_code)]` on `restore_entry`/`hard_delete_entry` (now consumed). New en + vi keys.

## Decisions

- **Trash-as-sidebar-folder** over the spec's filter `Select` — a user-directed UX change (friendlier,
  more discoverable). Documented deviation; the spec keeps a `[DRIFT]` marker.
- **Empty-trash loops `hard_delete_entry` client-side** (no new bulk command) — mirrors the shipped folder
  `on_empty`; a batched command is a later optimization only if the loop proves slow.
- **Empty-trash operates over `items`** (all trashed), not the folder/facet-filtered `visible`.
- **Trashed detail is a full tombstone** (hide favorite/history/tags) — a trashed entry shouldn't be
  copied, edited, moved, exported, favorited, or tagged.
- **Modal confirm for the two irreversible actions**, direct for Restore.

## Security

Permanent-delete + Empty-trash route through `hard_delete_entry` — verified in core to purge the Document
blob sidecar, version history, and audit `PermanentlyDeleted`; soft-delete (used for active-view Delete)
keeps everything for restore. No secret handling changes; no plaintext crosses IPC beyond the existing
copy path.

## Tests (+0)

Pure UI wiring over core-tested use-cases (`restore_entry` / `hard_delete_entry` are covered in
`vedge-core`), as with 3.1/3.3/3.5's UI portions — no new host tests. The empty-trash loop is inline and
the button only appears when there's something to empty, so no pure helper was warranted.

  `Signal::derive`; toast strings hoisted before `spawn_local`); the `folders`-derived-from-`items` gotcha
  (folder tree + breadcrumb + move/delete dialogs are all hidden in trash, so the stale tree isn't visibly consumed).
- **Human GUI smoke (`cargo tauri dev`) pending, not blocking:** the sidebar shows a **Trash** folder; it
  lists trashed entries (folders/smart-folders hidden, All/Unfiled/Trash visible, Trash highlighted); **All
  items** returns to the active vault; **Restore** returns an entry to Active; **Delete permanently**
  (confirm) removes it and, for a **Document**, the `.vedge_blobs/{id}.blob` file is gone from disk;
  **Empty trash** (confirm, count) clears all; a trashed entry's detail shows only Restore/Delete-permanently.

## Out of scope

A dedicated bulk `empty_trash` core command (the client loop suffices); retention-automation UI (core
already has it); a Trash count badge (the trashed list isn't loaded in active view — a count needs a
separate fetch); the rest of ticket #4 / other 3.7 low-sev items (3.6 takes only the trashed-detail swap).
