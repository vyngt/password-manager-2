# Slice 2.8 — Biometric Unlock

Optional **Windows Hello** unlock that gates release of the vault **KEK** from
hardware-backed storage. Encryption is unchanged and the master password stays the source
of truth — a stolen `.vdb` still needs password + Secret Key. Biometric just adds a
second, device-local custodian of the KEK. First slice to add a native OS-integration
crate (`windows`), spanning the whole stack (core → ipc → tauri → app). Spec:
`.../Specs/2.8 - Biometric Unlock`. Mockups: `2.8` (unlock) + `2.8b` (enroll dialog).

## The model

Normal unlock is `(master password + Secret Key) → 2SKD → Argon2id → KEK`. Biometric
replaces only the left of that arrow: the KEK (captured while already unlocked) is stored
behind an OS hardware gate; a user-present biometric check releases it, and a new
`unlock_with_kek` core path rebuilds the session from the KEK alone — no password, no KDF.

## What shipped

### Core — `vedge-core`

- **`BiometricAuthenticator` port** (`application/vault/ports/biometric.rs`) — a plain
  **sync** object-safe trait mirroring `KeychainProvider` (the underlying OS calls block
  and prompt). `is_available` / `is_enrolled` / `enroll` / `retrieve` / `disable`.
- **`unlock_with_kek`** — a method on `UnlockVault` mirroring `unlock_vault` from step 5
  (pin KEK → build index → audit → assemble), skipping the KDF/verify steps. The KEK is
  validated against the vault's own ciphertext: the first entry/tag that fails to decrypt
  surfaces as `WrongCredentials` (UI falls back to password) and no partial session is
  built. A 0-entry/0-tag vault has nothing to validate against and opens directly. Audits
  a distinct `AuditAction::BiometricUnlocked`.
- **`enroll_biometric`** use case — resolves the Secret Key, runs **one** Argon2 pass that
  both authorizes the re-prompted master password (`verify_hash` compare) and yields the
  KEK, then stores it behind the gate. Wrong password → `WrongCredentials`, nothing stored.
- **`change_password` lifecycle hook** (the load-bearing one) — `change_password` derives a
  *new* KEK and re-wraps every DEK, so an enrolled KEK goes stale. After the atomic commit
  and KEK swap it re-stores the new KEK if biometric is enrolled, so biometric keeps
  working across a password change with no re-enroll prompt.
- **Adapters** (`infrastructure/biometric/`): `MemoryBiometricAuthenticator` (test double),
  `stub` (`is_available() == false` — Linux/other), and `windows` (real Windows Hello).
  `platform_authenticator(crypto)` selects the right one; shells stay platform-agnostic.
- **Windows Hello** (`windows.rs`, `#[cfg(windows)]`): enroll creates a Hello-gated TPM key
  (`KeyCredentialManager`), signs a fixed challenge → `SHA-256(domain ‖ signature)` = wrap
  key → AEAD-seals the KEK (shared `CryptoProvider`) into the OS credential store
  (`keyring`, service `vedge-biometric`). Retrieve re-signs (Hello prompt) → same wrap key
  → decrypts. Resetting Windows Hello deletes the TPM key → `OpenAsync` = `NotFound`, so
  the credential **auto-invalidates on biometry change**. New `windows` crate under
  `[target.'cfg(windows)'.dependencies]`.

### Boundary — `vedge-ipc` / `vedge-tauri`

- Commands (`commands/biometric.rs`): `biometric_available` / `biometric_is_enrolled` /
  `biometric_enroll` / `biometric_unlock` / `biometric_disable`. `unlock` retrieves the KEK
  and routes it through `unlock_with_kek` (the `unlock_with_recovery_key` template) — no
  master password crosses for a biometric unlock; the KEK never leaves the backend.
- `CommandError::Biometric` (+ `ApiError::Biometric`, `envelope::kind::BIOMETRIC`) — all
  biometric failures (unavailable / not-enrolled / cancelled / failed) collapse into one
  variant; the shell falls back to the password path regardless.
- `AppState.biometric` wired in `setup/services.rs::compose` via `platform_authenticator`;
  the test composers + harness use `MemoryBiometricAuthenticator`. `change_password` command
  now passes the port through.

### App — `vedge-app`

- **Unlock screen** (`vault_launch.rs`): when the selected vault is enrolled, a Windows
  Hello button (fingerprint) is shown by default with a **"Use master password"** link that
  reveals the existing password row; any biometric failure falls back to it with a hint.
  Success reuses the shared `record_unlock` + `active.path` + nav tail.
- **Settings → Security** (`biometric_setting.rs`): a "Biometric unlock" toggle (disabled
  when unavailable) + an enroll `Dialog` (mockup 2.8b: three honest security notes + a
  master-password re-prompt → `biometric_enroll`); toggling off calls `biometric_disable`.
  This establishes the master-password re-prompt pattern (none existed before).
- `api/biometric.rs` wrappers; `biometric_*` i18n keys in `locales/{en,vi}/{unlock,settings}.yaml`.

## Manual smoke (human — `cargo tauri dev` on Windows; not runnable headless)

Settings → Security → enable **Biometric unlock** → master-password re-prompt → Windows
Hello prompt → enrolled. Lock → the launch screen offers "Unlock with Windows Hello" →
Hello → in; "Use master password" fallback works. Change the master password → biometric
still unlocks (refreshed KEK). Reset Windows Hello → biometric fails and falls back to
password. Disable → the stored key is removed; master password still unlocks. Console stays
warning-free.

## Deviations (recorded in the tracking note)

1. **`kek_check` deferred** — `unlock_with_kek` validates by decrypting the first
   entry/tag; a 0-entry/0-tag vault skips validation (nothing to protect). The explicit
   AEAD-of-constant `kek_check` for the empty-vault edge is deferred hardening — it would
   need a vault-schema migration for an edge case.
2. **macOS deferred to a future Touch ID follow-up** — this dev box is Windows; macOS
   native (`LAContext` / Keychain `.biometryCurrentSet`) can't be compiled or smoke-tested
   here. Linux/other = `is_available() == false` stub (password-only). (Not "2.8.1" — that
   number is the Vault Picker slice.)
3. **No dedicated IPC DTO** — commands return plain `bool`/`()` like `is_unlocked`; the
   enroll master password is passed as an inline command arg like `unlock_vault`.
4. **Enroll re-derives the KEK** from the re-prompted password (one Argon2) rather than
   reading `session.kek` — a single pass both authorizes the re-prompt and yields the KEK.
5. **The `change_password` KEK re-store lives in the core use case** (not the command), so
   it's covered by the core mock-authenticator test, matching how `unlock_vault` already
   calls the sync keychain port from an async use case.
6. **Windows storage = keyring blob + TPM wrap-key** (`KeyCredentialManager` signs → HKDF-
   style SHA-256 → AEAD-seals the KEK in the OS credential store). `is_enrolled` checks the
   blob (no prompt); a reset TPM key is caught at `retrieve` (→ password fallback).

## Deferred (per spec)

macOS Touch ID (a future follow-up); per-reveal biometrics; cross-device enrollment; the
explicit empty-vault `kek_check`.
