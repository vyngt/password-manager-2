# 5.2.2 — Export & Import Vault (2026-07-15)

The **SPACE** half of Decision ⑦. 5.2.1 owned TIME (snapshot / revert, in place, same vault);
this slice owns getting a whole vault **out of** this machine and **into** another one.

> **The `.vbk` is not a time machine. It is a vault in a suitcase.**

## The shape of it

5.2 had **one** verb — "restore a `.vbk` over a vault" — doing two jobs, and it needed **four**
confirmation dialogs to survive. Three of those existed *only* because an import could be aimed
at an existing file. Split the verb, and they evaporate:

| Verb | What it does | Destructive |
|---|---|---|
| **Back up to…** | write a `.vbk` anywhere | no |
| **Open backup** | materialize a vault at a path with **nothing there** | ❌ **never** |
| **Advanced ▸ Replace** | the demoted escape hatch | 🔴 yes — every guard, and it auto-snapshots first |

`open_backup` refuses an occupied destination outright: **no flag, no confirmation, no
override.** That one constraint deleted the uuid guard, the rollback gate, and finding **H2**
from the everyday path. All of them are **reinstated in full** on *Replace*, where they now
belong to exactly one operation.

## 🔴 The bug this slice found

`restore_vault` committed through `journal::commit`, which swaps the **whole home**. Since 5.2.1
the snapshot store lives at `<home>/snapshots` — *inside* that home. So **every `.vbk` restore
silently deleted every snapshot the vault had**, including the `pre-restore` undo point taken
seconds earlier to make the operation reversible. ⑭'s promise ("even the escape hatch is
undoable") was, in shipped code, a lie.

Nothing caught it, because no test asserted the continued existence of a directory nobody was
thinking about. Now:

- Replace commits through `commit_preserving(&[SNAPSHOTS_DIR])`.
- **`journal::commit` is deleted.** It had no legitimate caller left, and leaving it meant the
  next person to add a swap would inherit the silent default that eats the safety net. Callers
  must now *state* what survives their swap.
- `replace_preserves_the_snapshot_store` fails if anyone reintroduces it.

## Findings closed

- **H1** — the format guard was `!=`, so the day `BACKUP_FORMAT_VERSION` became 2, **every
  `.vbk` on every user's disk** would be refused as "unknown format". Now `>`: refuse newer,
  accept older, forever. Pinned by a test that *restores* a forged v0 archive end-to-end.
  🔴 **The same bug was found in the snapshot guard** (`revert_to_snapshot`, written one slice
  earlier) and fixed with it.
- **H2** — an unreadable target silently disarmed the uuid-mismatch guard. `read_target_identity`
  collapsed *"no vault here"* and *"a vault I can't read"* into one `None`. Now
  `TargetState::{Missing, Unreadable, Readable}`, so a caller **cannot** fall through the
  unreadable case by accident. `Unreadable` gets its own acknowledgement.
- **M3** — a backup carries `verify_hash_prefix` (additive, `#[serde(default)] Option<String>`;
  `format_version` stays **1**), so a preview can warn *before* the user commits time: "this
  needs the password and Emergency Kit in force on {date}". 🔴 `None` means **unknown**, never
  "same".
- **L2** — the `.blake3` sidecar was written and never read. `verify_archive` now verifies against
  it when present (absent → still passes; advisory, as promised). It is the only check that spans
  the whole file: the per-member check hashes against the very manifest an attacker would have
  rewritten.
- **②** — a copy opened beside a live original gets a **fresh `vault_uuid`**, and its Secret Key
  is carried across so it still opens on the master password alone. Without this, two divergent
  files share one `counter:{uuid}` keychain baseline and the original gets a **false rollback
  warning on every unlock, forever**.
- **⑧** — Settings ▸ Backup now shows *"never backed up"* from the `last_backup_at` column, never
  from `BackupCreated` audit rows (which `create_snapshot` also emits). A snapshot must not be
  able to silence "you have no backup".

## Also fixed (found in the scan, not by any test)

- 🔴 `remove_stale_recents` still tested `path.is_file()` — but 5.2.0 made `path` a *directory*.
  The registered `remove_stale_recent_vaults` command would have **deleted every healthy vault
  from the recents list**. Harmless only because nothing ever called it.
- `restore_over_an_existing_vault_replaces_it` was **passing because of H2**: it built its target
  by copying `vault.vdb` alone out from under a live session, so the config rows were still in
  the uncheckpointed `-wal` and the target was *unreadable* — which made 5.2b skip every identity
  check. It believed it was proving "a matching-uuid target is replaced". It was proving that an
  *unidentifiable* one is.

## Deviations from the spec

1. **The "stem trap" is dead.** The spec's ⚠️ #4 (and its test) target `derive_blob_root`, which
   5.2.0 **deleted**. Blobs now root at `<home>/blobs`. The concern survives in a new form
   (the destination home must be provisioned with `blobs/` **and** `snapshots/`) and is tested.
2. **No new keychain method, and no new migration.** The spec assumed a path-keyed keychain and a
   missing `recent_vaults.vault_uuid` column. 5.2.0 made the keychain uuid-keyed (so ②'s Secret-Key
   copy is two *existing* trait methods) and already added the column (5.2.2 just populates it).
3. 🔴 **No `mode=rw` fallback.** The spec proposed one, on the theory that most "unreadable"
   targets are a dirty `-wal` that `mode=ro` cannot replay. **Measured against a real crash image
   (300 KB uncheckpointed `-wal`, no `-shm`): `mode=ro` reads it fine.** The fallback would have
   been an unreachable branch that, on the one path it *could* run, **writes** to a vault the user
   has not unlocked — from a probe that runs against every recent at startup. The three-state
   `TargetState` is the real H2 fix and stands alone.
4. **`restore_vault` → `replace_vault_from_backup`.** The naming *is* the fix: H0 happened because
   one verb meant two things. (The `journal` internals keep their `restore-*` names — they are
   shared with `revert_to_snapshot` and are not a verb.)
5. **`open_backup` writes no audit row.** The materialized home *is* the source vault's DB and
   carries its full history; the first unlock records `Unlocked`. An audit row would mean opening
   and WAL-pinning a vault we were not asked to open.
6. **The `.vbk` path field is typeable, with Browse beside it.** A native file dialog cannot be
   automated, and the acceptance test has to be UI-driven — being *untestable* is how 5.2 shipped
   a restore button no user could reach (H0). Same pattern as the create wizard's Location field.

## Test hygiene: the e2e suite no longer pollutes your real credential store

Unlike every other external dependency, the **OS keychain is not faked** in e2e — the real
credential store is the only way to actually test it. So each run left real entries behind: a
Secret Key (`secret:{uuid}`) and a rollback baseline (`counter:{uuid}`) **per vault** — and this
slice's ② adds another pair for every duplicate a test opens.

Under the production `vedge` service those orphans are **indistinguishable from a developer's own
vault keys**. They are keyed on an opaque ULID, so you cannot tell them apart by looking; they
accumulate forever; and deleting the wrong one destroys a real vault (recoverable only via its
Emergency Kit). On this machine it had already reached **231 entries, of which 218 were orphans.**

- `resolve_keychain` (`vedge-tauri/src/setup/services.rs`) files e2e entries under
  **`vedge-e2e-test`** instead. Same **debug-only + env-gated** seam as `resolve_kdf_seam` /
  `resolve_biometric` (`cfg(debug_assertions)` **and** `VEDGE_E2E_KEYCHAIN_TEST`), so a release
  bundle compiles the branch out and can only ever reach the real `vedge` service — no env var can
  talk a shipped app into storing secrets elsewhere. Pinned by a test.
- `scripts/keychain_audit.ps1` + `mise keychain-audit` / `keychain-clean` / `e2e-clean`.
  The audit decides orphan-vs-live from **evidence** — the uuids of the vaults you actually have
  registered and on disk — and **refuses to delete anything if it cannot see them**, because
  "delete everything" is the wrong answer to "I can't see anything". (`scripts/` is no longer
  gitignored.)

## 🔴 Found by the pre-commit e2e re-run — Open backup was broken on Windows

The host suite was green. Clippy was green. And **`open_backup` failed 4 times out of 6 in the real app**:

```
io error: move the opened vault into place: Access is denied. (os error 5)
```

Opening a **duplicate** is the one path that opens the staged `vault.vdb` before committing (to mint its
fresh uuid — ②). `sqlx`'s pool close is not synchronous, so for a moment afterwards Windows still holds the
`.vdb`/`-wal`/`-shm` handles and **refuses to rename the directory containing them**. `open_backup` was
committing with a bare `std::fs::rename` on the async thread.

Two things were wrong, and both had to be fixed:

1. The rename must **retry** — `journal::rename_retrying` (M1) already existed for exactly this.
2. It must retry **on a blocking thread**. Retrying on the async thread starves the very pool-close task it
   is waiting for. `journal`'s own doc says this; `open_backup` wasn't listening.

**This is the same class of bug as the 5.2.1 field report** (*"an async close is not a close"*), in a new
place — and the host tests could not see it, because their runtime had threads to spare. Pinned by
`opening_a_duplicate_repeatedly_never_loses_the_rename_race`, which hammers the duplicate path six times.

*Process note: this was caught only because the closeout runs the e2e suite **after** the bug sweep and
**before** the commit. A "host tests pass, ship it" close-out would have shipped a headline feature that
fails most of the time on the platform it ships on.*

## Found by the pre-commit `/code-review high` (and fixed before this shipped)

- 🔴 **The Replace preview called its own target a duplicate.** `inspect_backup` ran ②'s scan
  unconditionally, and on the Replace path `known_vaults` (from recents) contains the target
  itself — so a normal Replace previewed as *"You already have this vault. Opening it makes a
  separate copy with its own identity."* while the user was in fact about to **overwrite** it.
  ② is an Open-mode question only. Pinned by `a_replace_preview_never_calls_its_own_target_a_duplicate`.
- The ⑭ auto-snapshot was taken **before** staging, so a staging failure (unsafe blob member, full
  disk, truncated archive) left a `pre-restore` undo point in the store for an operation that
  never happened. It now fires after staging succeeds, immediately before the swap.
- `find_duplicate` had been copy-pasted into both `inspect_backup` and `open_backup` — two copies
  of the scan that decides whether a user's original starts crying wolf forever. Now one, shared,
  and it returns the identity it read (removing a second open of the same database).
- `record_vault_uuid`'s doc claimed an existing uuid is never overwritten; the code overwrote it
  whenever it differed. The code is right (the vault file is the authority after a convert or a
  replace) — the doc was corrected.
- The Advanced ▸ Replace toggle was a raw `<button>`, violating the design-system rule in the
  Iteration Standards §7. Now a `Button`.
- An e2e "the original is untouched" assertion was a **tautology** (`entries.is_err() || …` — the
  original is locked, so `list_entries` always errors and the check always passed, even if the
  vault had been deleted). It now proves the point through the session-less `inspect_backup`.
