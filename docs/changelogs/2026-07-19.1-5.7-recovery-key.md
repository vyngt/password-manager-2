# Slice 5.7 — Recovery Key (2026-07-19)

**A forgotten master password used to be unsurvivable.** The Emergency Kit carries the *Secret Key*, not
the password — lose the password and the vault was gone. Slice 5.6 freed the word "recovery" (its
Secret-Key surface became `secret_key`); this slice ships the genuine credential the plan's **Decision ④**
always intended: an opt-in **Recovery Key** that reconstructs the vault KEK and forces a new password.

## The credential — `RK1-…`, bound to two documents

A 32-byte random Recovery Key, printed on a **Recovery Kit** document *separate* from the Emergency Kit:

```
KEK_rec = HKDF( Argon2id( 2SKD(Recovery Key, Secret Key), vault_salt, kdf_params ), "vedge-v1-recovery-kek" )
recovery_slot = AES-KW( wrap_key = KEK_rec, payload = KEK )     // 40 bytes, in vault_config
recover:  KEK = unwrap_dek( recovery_slot, KEK_rec )            // wrong R OR SK → AES-KW fails
```

Because `KEK_rec` is bound to `2SKD(Recovery Key, Secret Key)` — never the Recovery Key alone — **neither
document opens the vault by itself**, and because `R` is 256-bit random the offline floor stays the master
password (a user-chosen recovery phrase would have become the new floor — we deliberately don't offer one).
The AES-KW 8-byte integrity check enforces the two-document property at the unwrap: a wrong `R` or `SK`
fails cleanly (`WrongCredentials`), never a plausible-but-wrong KEK.

🔴 **The `RK1-` prefix (DRIFT from the spec's `B1-`).** The spec named the prefix `B1-`, but `B1` collides
with the Secret Key's own reserved version namespace (`A3`→`B1`→`C1`… on SK format changes). `RK1-` is
unambiguous and better serves the spec's "the two prefixes must be unmistakable" goal. Frozen at
introduction. The codec is the **generalized** `A3-` machinery (one shared set of Crockford-base32 +
HMAC-SHA256 helpers over a `KeyCodec` descriptor); a golden test pins the `A3-` output byte-identical so a
shipped Emergency Kit stays parseable, and a distinct checksum context (`vedge-v1-recovery-checksum`) makes
`A3-`/`RK1-` mutually unparseable.

## The couplings — where a recovery slot bricks if you forget it

- ③ **A KEK change deletes the slot.** The slot wraps the *old* KEK; after `change_password`/`rotate` rewrap
  every DEK, a stale slot would unwrap a dead KEK — a silent brick at the recovery moment. `change_password`
  nulls `recovery_slot` in the **same transaction** as the DEK rewrap. The load-bearing detail (C1): the null
  persists only because `RecoverySlot` is in `rewrap_all_deks`'s `update_columns` (unlike `save_config`,
  which omits it so a generic unlock can't clobber an enrolled slot). **No escrow** — a password change
  genuinely revokes recovery.
- ④ **Snapshots carry no live slot.** A snapshot is a `VACUUM INTO` byte-copy, so `create_snapshot` nulls the
  copied slot *before* hashing (Fix A — load-bearing: a revert reopens with the current KEK, so a live slot
  would silently re-arm a possibly-*revoked* Recovery Key). `rewrap_one` nulls it too (Fix B, belt-and-
  suspenders). `.vbk` backups keep their slot (a restore is a consistent whole-vault return).

## The recovery flow + the escalation gate

Recovery lives on the launch screen (the vault is locked). `unlock_with_recovery_key` opens the vault with
the KEK unwrapped from the slot, then the flow **forces a new master password** — the user forgot the old
one, so this path skips 5.6's current-password reauth. To keep "no-reauth password change" from becoming a
walk-up-attacker takeover on *any* unlocked vault (C2), it's gated on a **one-shot session capability**:
`unlock_with_recovery_key` stashes the typed Secret Key in `VaultSession.pending_recovery_reset`;
`change_password_after_recovery` consumes it (errors `NoRecoveryResetPending` otherwise), which both gates
the no-reauth change to a just-recovered session *and* feeds the SK to the forced change explicitly — so it
works even if the keychain re-store failed on a fresh device (C4). ③ nulls the slot as part of that change,
so recovery always ends off; the user re-enrols.

Enrolling **re-authenticates the current password** (DRIFT toward safety from the spec's frictionless
enroll: silently minting a Recovery Key on an unattended unlocked vault would be a stealthy backdoor).

## Revocation is honest — real revocation is 5.8

Revoke deletes the slot, turning recovery off for *future* copies. 🔴 Anyone who already copied the `.vdb`
keeps their old slot — truly revoking a leaked key is a full re-key (5.8). The UI copy says so.

## No schema bump (DRIFT-adjacent, documented)

`recovery_slot` is additive + nullable, so — per the `vault_uuid`/`commit_counter` precedent — there's **no
`schema_version` bump** (an older build ignores the column). The one gap: a **pre-5.7** build that changes
the password of an enrolled vault won't null the slot → dead recovery on downgrade. This is a documented
limitation (recovery-only, not data-loss; requires a downgrade), chosen over pinning enrolled vaults to
≥5.7. Migration `m20260718_100012_add_recovery_slot`.

## The Recovery Kit PDF

A sibling of the Emergency Kit renderer titled **"Vedge Recovery Kit"**, with the `RK1-` key + a QR and 🔴
instructions to keep it *separate* from the Emergency Kit. Unlike the Emergency Kit the Recovery Key is
show-once and never stored, so the PDF is rendered from the display string passed back from the transient
enroll state. 🔴 **`R` never persists** — generated server-side, crosses to WASM once as the show-once
display, rendered into the PDF in the shell, dropped.

## DRIFTs (documented)

1. **Prefix `RK1-`, not the spec's `B1-`** (avoids the SK version-namespace collision; frozen).
2. **Enroll re-authenticates the current password** (spec's enroll was frictionless; this hardens against a
   stealthy backdoor).
3. **No `schema_version` bump** (spec's decision ②, kept) → a pre-5.7 build can strand the slot on a
   downgrade password change (documented, recovery-only).
4. **The recover command returns `()` not the outcome DTO** — recovery has no keychain-status to surface
   (the forced change re-stores the SK anyway).
