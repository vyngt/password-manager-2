# Slice 2.7 — Entry History

Full-entry version snapshots on edit, with a **Version history** panel to view /
reveal / copy / restore prior versions. The first Phase-2 slice with a **new SQLite
table** (`entry_history`), spanning the whole stack (core → ipc → tauri → app). Spec:
`.../Specs/2.7 - Entry History`. Mockup: `.../Mockups/2.7 - Entry History` (a Card, to
prove it's not password-only).

## What shipped

### Storage & crypto — `vedge-core`

- **New migration** `m20260418_100006_create_entry_history` — a child table keyed by
  `entry_id` (no FK; the schema has none). Columns: `id, entry_id, version,
  cipher_suite, nonce, ciphertext, changed_at` + an `(entry_id, version)` index. The
  table + its index live in the *same* new migration so existing dev vaults pick it up
  (editing the already-applied indexes migration would not re-run).
- **No key material in snapshots.** `EntryHistoryRow` stores only the superseded
  ciphertext + nonce + version — **never `dek_wrapped`**. A snapshot is decrypted by
  unwrapping the DEK from the **live `entries` row** (the per-entry DEK is stable for
  the entry's life; `change_password` re-wraps it O(1) without rewriting ciphertext),
  and authenticated against the snapshot's *own* version via `entry_aad`. So history
  survives a master-password change — guarded by a dedicated test.
- Parallel plumbing mirroring `entries`: domain `EntryHistoryRow`, SeaORM entity,
  mapper, and five `VaultRepository` methods (`insert_history`, `list_history`,
  `get_history`, `delete_history_for_entry`, `prune_history_keep`).

### Use-cases — `vedge-core` `use_cases/entry_history.rs`

- **Capture on edit** — `update_entry` snapshots the pre-update row *before*
  overwriting it: a pure byte-copy of the existing ciphertext (no decrypt), then a
  prune to the cap. Only the `update_entry` *use-case* captures — metadata-only
  mutations (favorite/tags/sort/move) deliberately don't, so history stays a log of
  real content edits.
- `list_history` — decrypts the live version + every snapshot **server-side only** to
  diff *field names* (a generic top-level JSON-object diff, UI-meta excluded), and
  returns metadata (version, changed_at, changed_fields) — **no secret values leave the
  backend, and it is not audited.** The current live version rides as `history_id = None`.
- `get_history_value` — the sanctioned reveal: returns the decrypted payload and audits
  `Viewed`, mirroring `get_entry`.
- `copy_history_field` — copies a prior field to the OS clipboard (auto-clear) through
  the shared `copy_field` machinery; the plaintext never returns to WASM.
- `restore_from_history` — decrypts the snapshot and routes it back through
  `update_entry` (which snapshots the now-current value first); no plaintext out.
- **Retention** = `const HISTORY_MAX_VERSIONS = 20`, pruned on capture (oldest dropped).
- **Cascade** — `hard_delete_entry` and the trash-purge path (`hard_delete_trashed_before`)
  both purge an entry's history explicitly (no FK cascade).

### Boundary — `vedge-ipc` / `vedge-tauri`

- `HistoryEntryDto { history_id: Option<String>, version, changed_at, changed_fields }`
  (`history_id = None` = current live version).
- Four commands (`list_history`, `get_history_value`, `copy_history_field`,
  `restore_history`) mirroring `get_entry` / `set_favorite` / `list_entries`; a
  `history_to_dto` mapper; a new `VaultError::HistoryNotFound` → `CommandError::NotFound`.

### UI — `vedge-app`

- **Version-history panel** (`features/vault/entry_history.rs`): a `Dialog` opened from
  the detail via a `target` signal (the `FolderCustomize` pattern). Rows show date +
  relative time, changed-field `Badge` chips, and per-row reveal (eye) / copy /
  **Restore** (prior versions only, with a confirm banner). The current row is
  highlighted; its reveal/copy use the live `get_entry` / `copy_field` paths. Reveal
  shows the version's primary secret via `SecretDisplay`; copy of Login/Card/ApiKey
  routes through the backend clipboard.
- **Detail entry point** — a "Version history" `IconButton` in `vault_detail`'s header,
  gated to the ✅-Full types (Login, Card, SSH key, API key, Env vars, Note, Identity).
- Pure, host-tested date helpers `long_date` (`Jul 3, 2026`) + `relative_time` (bucketed
  "N days/weeks/months ago") beside `short_date` in `entry_view.rs`.
- i18n: `history_*` keys added to `locales/{en,vi}/vault.yaml` (no `build.rs` change).

## Tests

  retention prune, **history-decryptable-after-password-change** (the load-bearing test),

- **app (host)**: `long_date` / `relative_time` bucketing.

## Manual smoke (human — `cargo tauri dev`; not runnable headless)

Edit a Card (or Login) → open Version history → prior versions appear dated with
changed-field chips; reveal / copy a prior value; Restore → becomes current **and**
snapshots the replaced one; change the master password → reveal still works; Folder /
Document / Unknown hide the panel; console stays warning-free.

## Deviations (recorded in the tracking note)

1. **Capture in the `update_entry` use-case only** — metadata-only mutations don't
   snapshot (content-edit log; avoids a favorite-spree evicting real versions).
2. **A 4th command `copy_history_field`** beyond the spec's three, to honor the security
   checklist's "copy routes through the backend clipboard, not a rendered value."
3. **`HistoryEntryDto.history_id` is `Option`** so the current live version rides the
   same list.
4. **Retention is a `const 20`** (no `VaultConfig` column) — configurable retention deferred.
5. **`changed_fields` via a generic JSON-object diff** (not per-variant), computed on
   `list_history`; chip labels reuse existing field i18n where available, else prettify
   the raw key.
6. **Document is excluded from the history button** (the spec's "metadata only" row):
   Documents never route through `update_entry` (non-editable), so they accumulate no
   snapshots, and restoring old metadata would carry a stale blob nonce. Excluding them
   matches the spec's ✅-Full set exactly.

## Deferred (per spec)

summary; history export; versioning a Document's file bytes.
