# Slice 5.4 — The WASM-Secret Sentinel

Generalizes the 4.2 TOTP "door" to **every** credential secret. Before this slice `ARCHITECTURE.md`'s egress
rule — *"only non-invertible derivatives cross to WASM"* — was true only for the TOTP seed; `get_entry`
still shipped `password`, recovery codes, card `number`/`cvv`/`pin`, ssh `private_key`/`passphrase`, api
`key`/`secret`, env-var values, and identity `national_id` to the renderer as plain strings on **every
open**. Now they don't. Spec: `.../Phase 5 - Data Safety & Recovery/Specs/5.4 - The WASM-Secret Sentinel`.
One PR, two internal commit groups (reveal doors → the seal), each a green checkpoint.

## 🔴 Read this or the slice reads as a failure: rarely & audibly, not never

A password has no permitted derivative — the password **is** the secret, so a "reveal password" must return
the real password. 5.4 cannot stop secrets crossing. **It makes them cross rarely and audibly:**

| | Before | After |
| --- | --- | --- |
| Open an entry | 🔴 the password crosses and **lives in JS for the session** | ✅ nothing crosses — `has_password`/count |
| Copy a field | ✅ never crosses (3.2's backend `copy_text`) | ✅ unchanged |
| Edit name / tags / url | 🔴 the password crosses (round-trips to save) | ✅ nothing crosses (`Unchanged`) |
| Reveal | *(no such op — it was just there)* | 🟡 crosses, **on an explicit click, audited** |

The win is the **ratio**: the plaintext crossed on every open; now it crosses only when a human deliberately
asks, and the audit log records that they did.

## Group 1 — the reveal doors (additive; the app was unaffected)

- **`AuditAction::SecretRevealed`** — a new variant appended to the enum / `ALL` / `as_str` / `parse`, to
  `vedge_ipc::ACTION_NAMES` (the compile-tied count test stays green), the app's filter-array length, and
  en/vi `action_secret_revealed`. **The audit log now distinguishes *browsing* from *extraction*** — before
  5.4, `get_entry` and `copy_field` **both** wrote `Viewed`, so the security-review surface couldn't tell
  "opened 40 entries" from "extracted 40 passwords."
- **`copy_field` and `copy_history_field` now audit `SecretRevealed`** (both extract a secret to the
  clipboard); `get_entry` / `get_history_value` keep `Viewed`.
- **`reveal_field`** — the audited twin of `copy_field`: same `FieldSelector`, same decrypt path
  (`extract_field` is now `pub(super)`), but the plaintext is **returned** to the renderer instead of going
  to the clipboard. Audited **per call, no dedup** (unlike `TotpRevealed` — a TOTP code auto-refreshes; a
  field reveal is always a deliberate act). **`reveal_history_field`** is its snapshot twin. Both get a
  Tauri command + registration + an `api::entry::*` bridge.

## Group 2 — the seal (the compile-coupled wire + core + form change)

### The door is one shared converter

The outbound secret-copy happens in **`vedge-tauri/src/dto/entry.rs::payload_to_dto`**, shared by both
`get_entry` and `get_history_value` — so sealing that one function **closes both doors at once** (the spec's
⚠️ "second door" was the same change, an altitude win). It now emits `SecretUpdateDto::Unchanged` +
presence/counts/keys instead of `.expose_secret()`; `Note.content` (the entry's whole substance) keeps
crossing.

### The bidirectional DTOs + the inbound sentinel

Each payload DTO is bidirectional — `LoginPayloadDto` already carried `has_totp` (out) + `totp` (in), so each
sealed secret became the same pair: a `has_*`/count (out) + a `SecretUpdateDto` intent (in).

- New `vedge-ipc/src/secret_update.rs`: `SecretUpdateDto {Unchanged,Set,Clear}`, `SecretListUpdateDto`
  (recovery codes), `EnvVarUpdateDto` (keyed rows). Kept **distinct** from `TotpUpdateDto` (identical JSON,
  but a TOTP `Set` carries a validated Base32 seed — one named type per concept).
- Revised the 6 payload DTOs; dropped `EnvVarDto` from the payload path. `has_*` only for **optionals**
  (required secrets are constant-`true`).
- 🔴 **`Unchanged` is the serde default, and that is the whole safety property** — a form that never touches a
  field sends no field → it deserializes as `Unchanged` → the stored secret is carried forward. **A dropped
  field preserves the secret; it never wipes it.**

### The resolver — one exhaustive site, the anti-silent-wipe guard

New `vedge-core/domain/vault/secret_update.rs`: a per-payload-variant `SecretUpdates` bundle + `resolve_secrets`
that fills the built payload's sealed fields from the intents against the decrypted `old` (or `None` on
create). It is **one `match` with no `..`** — adding a sealed field to a payload *forces* a field here and
*forces* it to be handled; a skipped resolution leaves an empty placeholder that any round-trip test catches
loudly, instead of silently wiping one field. `payload_from_dto` now returns `(EntryPayload, SecretUpdates)`
with placeholder secrets.

- **Clear policy (enforced in the resolver, not the form):** required secrets (password, card number/cvv,
  ssh private key, api key) **reject** `Clear` and `Unchanged`-on-create (`VaultError::RequiredSecretCleared`);
  optionals allow `Clear → None`; env-var rows reject `Clear` (removal = omit the row), reject a duplicate
  key, and reject `Unchanged` for a key with no stored value.
- **Asymmetric resolution point** (a pragmatic deviation from the spec's "one site"): create has no prior
  entry, so its **command** resolves the intents (`old = None`) into a complete payload — `create_entry` core
  is unchanged (zero churn for ~60 create call-sites). Update needs the decrypted old, so it threads `secrets`
  into core. Both still call the single atomic `resolve_secrets`. `SecretUpdates::set_all` /
  `UpdateEntryInput::full` bridge internal callers (import, restore-from-history) that already hold a complete
  payload.

### The edit form (`entry_form.rs`) — empty fields, intent, reveal

- `from_payload` no longer copies plaintext; sealed fields start **empty** with `editing = true` + the
  presence flags. `to_payload` derives a `SecretUpdateDto` per field via `required_intent` /
  `optional_intent`: a non-empty value → `Set`; an empty required field on an editing form → `Unchanged`
  (**keep the stored secret**); an empty optional with none stored → `Clear`.
- 🔴 **The placeholder says "Unchanged — type to replace"** on an editing form — never a fake `••••` value
  (which would round-trip literal dots into the vault). No strength meter is shown on an untouched field
  (there's nothing to score).
- **A per-field Reveal button** (`RevealCtx`, edit mode only) calls the audited `reveal_field` and fills the
  field — the "let me check it before I change it" flow the seal otherwise removes.
- Recovery codes have no editor → the form always sends `Unchanged` and the server carries them forward
  (sealing them would otherwise wipe them on every edit).

### History (`entry_history.rs`)

`do_reveal` migrated from extracting the secret out of a (now-sealed) payload to the audited
`reveal_field` / `reveal_history_field`; a Note's content still rides the payload fetch (it isn't sealed).

## Documented deviations (see the tracking note's Gotchas)

- ⚠️ **`FieldSelector` covers only password / card-number / cvv / api-key** (and env-var values). So the
  per-field **Reveal button** ships for the password today, and **history reveal** covers Login / Card /
  ApiKey / Note; reveal for pin / passphrase / ssh-private-key / api-secret / national_id is **deferred**
  (needs a `FieldSelector` extension). Those values are still **copyable** where a `FieldSelector` exists, and
  are still fully editable (empty = keep, type = replace).
- **Explicit Clear-in-form for optional secrets is deferred** — the resolver supports and tests `Clear`, but
  the form has no "remove this optional" affordance yet (empty + stored = keep). Renaming an env-var key
  requires re-entering its value (the sealed value can't follow a rename).
- `national_id` **is sealed** (it's `SecretString`-wrapped and is Identity's credential field) — a deliberate
  deviation from the spec's prose "Identity fields keep crossing," consistent with the spec's own
  property-rule. The other Identity fields (name/email/phone/address/dob) stay plain.

## Tests

Host **828** (was ~808). The acceptance bar: a **per-field wire door test** across all 6 payload types
asserts every secret string appears **nowhere** in the serialized DTO (`vedge-tauri/dto/entry.rs`), plus the
wasm `wire_wasm.rs` Login door and the `vedge-ipc` serde-default test. 9 domain resolver unit tests
(Unchanged-carries / Set-replaces / required-rejects-Clear / optional-Clear→None / env-var keyed carry, dup,
missing). The **"edit-name-only does not change the password"** integration test proves spec #5 (the
ciphertext's nonce rotates; the decrypted password is identical). The audit-distinguishability test proves ③
(`get_entry → Viewed`; `copy_field` + `reveal_field → SecretRevealed`, distinguishable). **e2e (+1)**
`reveal_a_password_via_ui`: open edit → the password is not in the DOM → Reveal → it is → the audit shows a
`SecretRevealed` row.

Export / import are **untouched** — 5.3's export DTO is a separate type by design, and the import preview is
already derivatives-only. The duplication people wanted to DRY away is exactly what kept this slice small.
