## Headline — the 3.8 test seams, proven release-impossible by a real release build

3.8 shipped three test-only seams (Argon2 fast-KDF, in-memory biometric, the lock-on-blur JS hook),
each gated on **both** `cfg(debug_assertions)` **and** an explicit `VEDGE_E2E_*` env var. 3.8 could
only prove their absence by a **grep of source** — a full release build overran the session budget.
Since a fast-KDF path reachable in a shipped password manager would gut the vault's key-stretching,
3.9 closes that gap with the real thing:

- `cargo build --release -p vedge-tauri` (`debug_assertions` off) compiles the
  `#[cfg(not(debug_assertions))]` twins — `resolve_kdf_seam → None`,
  `resolve_biometric → platform_authenticator` — and drops `KdfParams::fast`,
  `test_set_dialog_in_progress`, and `install_test_hooks` entirely.
- The env-var string literals **`VEDGE_E2E_FAST_KDF`** and **`VEDGE_E2E_BIOMETRIC_MEMORY`** — which
  appear only inside the debug-gated seam fns (`vault.rs::resolve_kdf_seam`,
  `services.rs::resolve_biometric`) — are **absent** from the release binary (a grep of the built
  artifact returns nothing). Command + output recorded in the 3.9 tracking note.

## What shipped (docs + reconcile — one doc-comment is the only `.rs` change)

`features/generator/generator_panel.rs` claimed entropy bands come "**not** from the
`password_strength` (zxcvbn) scorer" — but `password_strength` is **not** zxcvbn: it's an explicit
length + char-class heuristic (`password_strength.rs:1-5` says so), and `zxcvbn` is in **no**
`Cargo.toml`/`Cargo.lock`. The `(zxcvbn)` label had already propagated into 3.1's notes and would have
misled Phase-4 password-health work. Reworded to name it a heuristic and explicitly *not* zxcvbn.
