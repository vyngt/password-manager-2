# Slice 5.6.0 — Tag Keys (2026-07-18)

**A master-password change permanently destroyed any tagged vault — and every snapshot of it.**
Fixed by giving tags a per-row DEK and deleting the ability to seal a tag under the KEK. `.0` =
foundation: **5.6 (Credential-Lifecycle UI) could not ship the change-password button until this landed.**

## The bug

Tags were the *only* thing in VEdge sealed directly under the vault KEK (`crypto.rs:43` doc:
*"no per-row DEK for tags"*). Everything else has a per-row DEK that survives a KEK change by being
re-wrapped. `change_password` re-wrapped every entry DEK + `verify_hash` and **never touched tag rows**:

```
new password → verify_hash matches → KEK_new → decrypt_tag_row(row, KEK_new)? → FAILS → unlock fails
old password → verify_hash mismatch                                            → rejected
```

Neither password opened it; the Emergency Kit carries the *Secret Key* (not what broke). And 5.2.1's ⑬
`rewrap_snapshots` had the identical omission → it **propagated the brick into every snapshot**. It was
unreachable in production (`api/password.rs` is still `#[allow(dead_code)]` — no UI), so the fix is pure
forward with zero already-bricked vaults. Reproduced first (`tag_keys::tagged_vault_survives_password_change`
fails on the pre-fix code with `DecryptionFailed`), then fixed.

## The fix — a deletion, not a rewrap-in-place

Tags now carry a per-row DEK wrapped under the KEK, exactly like entries (`tags.dek_wrapped BLOB NULL`,
migration `m20260718_100011`). The trait's `encrypt_tag` / `decrypt_tag` are **deleted**; a single read-only
`decrypt_legacy_tag` remains for rows not yet migrated.

> 🟢 **The achievable invariant (stated honestly):** KEK and DEK are both `[u8; 32]`, so deletion is not
> compile-unrepresentable. What the deletion *does* guarantee is **no WRITE path uses the KEK as an AEAD
> key — the KEK only wraps DEKs (AES-KW) and, on read, decrypts legacy tags through the one greppable
> `decrypt_legacy_tag` door.** A behaviour guard (`half_migrated_vault_reads_and_completes`) locks "every
> tag write carries a DEK." New `use_cases/tag_crypto.rs` holds the three shared primitives —
> `seal_tag_payload` (write), `open_tag_row` (dual-path read), `rewrap_tag_row` / `migrate_legacy_tag`.

**At-unlock migration (one place, both paths).** `build_index` — the single folded unlock loop 5.3c
created — migrates each legacy (NULL) tag to a fresh DEK and writes it back. Idempotent (a DEK-sealed tag is
a no-op, no nonce churn); a write error fails the unlock; a crash mid-loop strands nothing (the next unlock
re-migrates the NULLs). Mirrors the `backfill_vault_uuid` pattern 5.2.5 kept.

**Both fixes fall out of the schema change.** `rewrap_all_deks` gained a `tag_updates: &[TagRow]` arg and
writes the tag rows in the SAME transaction as the entries + `verify_hash` (so `verify_hash` never advances
past a tag left under the old KEK). `change_password` and `rewrap_snapshots::rewrap_one` both build it —
the snapshot fix is inherited.

## 🔴 Blast radius the spec's table undercounted (this family's pattern — twice more here)

Verified by property ("what reads/writes a tag's ciphertext?"), an Explore sweep + an adversarial red-team
found **two omitted sites and two latent re-bricks**:

- **U1 — biometric reuse.** `encrypt_tag` / `decrypt_tag` doubled as a generic KEK-wrap in
  `biometric/windows.rs` (sealing the KEK itself under a Hello-derived key, fixed `WRAP_AAD` — nothing to do
  with tags). Deleting them per the spec would have broken biometric unlock. Rehomed to
  `encrypt_entry` / `decrypt_entry` (byte-identical — the same `aead_*` helper).
- **U2 — `schema_version` writers.** `CURRENT_SCHEMA_VERSION` is read only by the three `.vbk`-restore
  guards, never on unlock, and the one production writer (`create_vault`) hardcoded `1`. Bumping the
  constant alone would have been inert for new vaults → a v2 vault's `.vbk` stamps `1` → a v1 build restores
  it → bricks on DEK-sealed tags. Fixed: `create_vault` writes `CURRENT_SCHEMA_VERSION`; existing vaults
  bump on unlock (`bump_schema_version`, riding `save_config`); and an **unlock-time guard** now refuses a
  vault whose `schema_version` exceeds this build (the spec's "refuses cleanly" intent — the `.vbk` guard
  alone never covered a direct open). The other four hardcoded-`1` sites are `#[cfg(test)]` fixtures and
  stay `1`.
- **B1 — `update_tag` dropped `dek_wrapped`.** It wrote only `nonce`/`ciphertext`/`updated_at` (unlike
  `update_entry`). The migration would have written DEK-ciphertext with `dek_wrapped` still NULL → the next
  unlock's legacy path decrypts DEK-ciphertext under the KEK → AEAD fail → **a self-inflicted brick.** Fixed
  + a repo round-trip test (`vault_db::tags_crud_round_trip`) that asserts `dek_wrapped` survives insert AND
  update.
- **B2 — `rewrap_one` must not skip NULL snapshot tags.** The revert path reopens via `build_index`, which
  **hard-fails** on a tag decrypt error — it does NOT go through the best-effort `read_snapshot_tag_names`
  (only import/tweezers reaches that). Skipping a NULL snapshot tag while advancing `verify_hash` = a
  half-rewrapped snapshot → revert → neither password opens it. Fixed: `rewrap_one` **migrates** NULL
  snapshot tags in the same txn (legacy-decrypt under `old_kek` — which succeeds exactly when the entry
  rewrap does — then re-seal under `new_kek`); a tag it genuinely cannot read aborts the whole snapshot
  before any write. Regression test `legacy_snapshot_tag_is_migrated_not_skipped_on_password_change`.

## `schema_version` 1 → 2, and H1 pays for itself

The at-rest tag ciphertext moves from KEK-sealed to DEK-sealed, which a v1 build cannot read, so
`CURRENT_SCHEMA_VERSION` bumps to 2. This is where 5.2.2's `!=` → `>` guard (H1) earns its keep exactly as
predicted: a **v1 `.vbk` restored by a v2 build** passes (`1 > 2` is false) → its tags migrate on the next
unlock; a **v2 `.vbk` restored by a v1 build** is refused cleanly (`2 > 1`). Had the guard stayed `!=`, the
bump would have orphaned every archive on disk. All four `format_version > *_FORMAT_VERSION` sites (a
separate axis) were re-verified as `>`, and the H1 canary `an_older_format_still_opens_forever` stays green
and unmodified.

## 5.3c's best-effort snapshot-tag path is KEPT

`read_snapshot_tag_names` now reads both shapes (dual-path), so a rewrapped snapshot's DEK-sealed tags
resolve. Its best-effort degradation (an unreadable tag table → no tag names, never a refused recovery)
stays as defence for a genuinely stale, hand-copied snapshot — not dead code (Standards §7). Its regression
test `tweezers_recovers_when_snapshot_tags_are_unreadable` stays green.

## Scope

`vedge-core` only — no wire/DTO/UI change (tags cross to the UI as names/ids, never ciphertext). No new
dependencies. `.vbk` `format_version` unchanged; vault `schema_version` 1 → 2. This discharges the P0 filed
in 5.3c's review.
