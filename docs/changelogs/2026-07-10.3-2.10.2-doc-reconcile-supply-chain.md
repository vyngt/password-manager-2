## A. Reconciled the stale top-level design docs

`ARCHITECTURE.md` described the **deprecated v1/v2** stack end-to-end — **SQLCipher** full-DB
encryption, **AES-GCM**, **Sea-ORM for everything**, `/app`·`/frontend`·`/backend` crate paths that
don't exist, `business/domain` layers, `vault_item.rs` entities. For a password manager that's the
worst doc to have stale (it named *SQLCipher — the exact thing v3 replaced* — as the encryption).

**Rewrote it** to the code-verified v3 reality (every claim cross-checked against `vedge-core`):

- The real 7-crate map + the `application/`·`domain/`·`infrastructure/` layers.
- The crypto lifecycle: **2SKD** (HKDF-SHA256 of master password + 16-byte Secret Key) → **Argon2id**
  (256 MiB) → master key → HKDF-expanded **KEK** + verify-hash; **per-entry, per-write DEK** wrapped by
  **AES-KW** under the KEK; payloads sealed with **XChaCha20-Poly1305** (AAD = entry ULID ‖ version;
  tags sealed directly under the KEK); `SecretMem` mlock/zeroize; **plain bundled SQLite via Sea-ORM**
  (both `app.db` and the vault `.vdb`), ciphertext per-row, **not SQLCipher**.

**Swept the design vault:** `02 Architecture/02 - Technology Stack` (stale `ring`/`age`/`aes-gcm`
"Encryption" row + "encrypted SQLite" → the real RustCrypto stack + "plaintext file, per-row
ciphertext", with a dated status line; the Elixir/PKI/sync rows left as legit forward-looking vision);
`01 Concepts/04 - Cryptography and Vault Security` (a *research* doc that correctly names
XChaCha20-Poly1305 primary — added an as-built status note flagging that the AES-GCM "fallback" was
never implemented, there's no BLAKE3 commitment header, and the real AAD/recovery differ from the
sketch). The `03 Specs/10 Core` crypto/DB notes were already accurate.

## B. Added the supply-chain gate

No `cargo audit` / `cargo deny` existed. The baseline was **not clean** — 5 vulnerabilities + 1 unsound
+ 20 unmaintained + `aes 0.9.0` **yanked** (a direct crypto dep). Established a clean gate:

- **Fixed** what a safe `cargo update` fixes: `anyhow` (RUSTSEC-2026-0190 unsound), `crossbeam-epoch`
  (-0204), `rustls-webpki` (-0104), and moved `aes` off the yanked `0.9.0` → `0.9.1` (aes-kw allows it).
- **`deny.toml`** (new): `[graph] targets` = the desktop platforms; `[advisories]`
  `unmaintained = "workspace"` (don't fail on the deep transitive GUI/PDF unmaintained tree) +
  **dated, reasoned `ignore`s** for the `printpdf 0.7` cluster (lopdf / quick-xml — we *generate* PDFs,
  never parse untrusted ones; a printpdf bump is tracked in the Phase-3 backlog); `[bans]`
  `multiple-versions = "warn"` (the crypto version spread is documented-structural); `[licenses]` a
  permissive SPDX allowlist (no GPL/AGPL anywhere) + `private.ignore`; `[sources]` crates.io only.
- Marked the 6 first-party crates **`publish = false`** (correct metadata — they're a desktop app +
  internal libs, not crates.io packages — and what makes the license check pass).
- **Expanded** the thin/misleading crypto pin-rationale comment in `vedge-core/Cargo.toml` to document
  the deliberate version spread.
- **`mise audit`** task = **`cargo deny check`** (the authoritative gate — build-graph / feature /
  target aware, so it flags advisories only for crates we actually compile) + `cargo-audit`/`cargo-deny`
  in `mise setup`; documented in `docs/testing.md`. `cargo audit` is kept as a supplementary *manual*
  tool but is **not** in the gate — its raw-`Cargo.lock` scan over-reports feature-gated-unused crates
  (`rsa`, `quinn-proto` — `cargo tree -i` finds neither), and gating on those would mean misleading
  `ignore`s for CVEs in crypto crates we don't compile. Kept out of the default `mise ci` (needs network
  + the tools) — an opt-in / pre-release gate, like `mise e2e`.
