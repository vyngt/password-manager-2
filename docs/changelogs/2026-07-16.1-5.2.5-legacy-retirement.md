# 5.2.5 — Legacy Retirement (2026-07-16)

The **5.2.x family's last chapter, and the one that ends it.** The family is *the vault as an
object on disk*: a folder (5.2.0) → snapshot it (5.2.1) → move it (5.2.2) → its identity follows it
(5.2.3) → destroy it (5.2.4) → **retire its old shape (here)**.

VEdge is pre-1.0 with **zero users**. Every line that exists to migrate *from* a state no artifact
is in serves nobody, and will serve nobody. This slice retires that one-shot migration surface —
**and nothing else** — behind a rule and two guardrails, because this is the exact shape of
operation that shipped two bugs at 2.10.1 (a "dead-code sweep" that deleted wrappers with "no call
site" and killed retention → repaired 4.6a, and recovery → shipped as a live user dead-end, repaired
5.1).

> **The rule (the actual deliverable): delete by PURPOSE-GONE, never by CALL-SITE-ABSENT.** A thing
> is retirable *iff no artifact that could need it can still exist* — not "nothing calls it."

## 🔴 The precondition: prove absence *before* you burn the tools

`KeychainProvider::migrate_secret_key` and `BiometricAuthenticator::purge_legacy` are the **only**
code that will ever reach the legacy `vault:{path}` keychain entries and the path-hashed Windows
Hello credentials on this machine. Delete them with one legacy artifact still on disk and it is
stranded forever — B1's failure mode, self-inflicted by the cleanup. So the order is not negotiable:
**convert every vault → `mise legacy-audit` green → then delete.**

### `scripts/legacy_audit.ps1` + `mise legacy-audit` — the deliverable, and it runs first

A read-only, **never-deletes**, prove-absence audit (extends 5.2.2's `keychain_audit.ps1` idioms).
It exits non-zero on **any** legacy artifact **or on cannot-enumerate** — 5.2.2's discipline,
verbatim: *"'delete everything' is the wrong answer to 'I can't see anything.'"* Cannot-see ⇒ FAIL.
Five probes:

1. Every `vault_registry.path` ends in `.vedge`, is a directory, holds `vault.vdb` — zero `.vdb` rows.
2. No bare `*.vdb` file / `*.vedge_blobs/` dir beside any home, nor in any `backup_dir`.
3. Zero `vault:*` accounts under the `vedge` keychain service.
4. Every `vedge-biometric-*` credential hashes (`URL_SAFE_NO_PAD(sha256(uuid))`) to a known live
   vault — a path-hashed one would not.
5. Every reachable `vault_config.vault_uuid` is non-null (no pre-4.6 vault).

**It did its job the first time it ran on the real machine:** green on 4 probes, but probe 4 flagged
a genuine orphan biometric credential — a `vedge-biometric-*` entry whose vault was entirely gone
(no registry row, no `secret:`/`counter:` key). That is exactly the residue this slice must ensure is
cleaned *before* the one-shot tools are deleted. Removed on-device, re-run → **PROVEN CLEAN** (8 live
vaults, zero legacy). Only then was a line deleted.

The audit also **fixed a live bug it inherited:** 5.2.4's `recent_vaults` → `vault_registry` rename
had silently broken `keychain_audit.ps1`'s `SELECT … recent_vaults` (it would then refuse to delete,
misreading every entry as an orphan). Retargeted to `vault_registry`.

## ⚠️ `backfill_vault_uuid` — kept, as its own decision (in writing)

The spec flagged this as "the §A entry most likely to be wrong; treat it as its own decision." It is
**kept.** The `vault_uuid` column is nullable with **no SQL default and no data backfill** —
`backfill_vault_uuid` (fires on every unlock, riding the unconditional `save_config`) is the *only*
thing that fills it. `create_vault` mints, but the three import/restore paths — `open_backup`
(relocated branch), `replace_vault`, `revert_to_snapshot` — **preserve** the source uuid rather than
mint one, so a null could propagate through them from any externally-supplied archive. `create_vault`
is therefore not provably the sole minter, we cannot prove "no artifact that could need it can still
exist," and deleting it would strand any null-uuid vault forever (keychain + biometric unlock break).
It stays; its repository test (`vault_uuid_backfill_does_not_duplicate_config_row`) stays.

## 🔴 Deliberately untouched (verified at the gate)

- **§B forward-compat.** `format_version > CURRENT` (open_backup, replace_vault, inspect_backup,
  revert_to_snapshot) + `schema_version > CURRENT_SCHEMA_VERSION` + the `#[serde(default)]` manifest
  fields. These are *how the format can ever evolve* — `!=` would be bug H1 (already introduced
  twice). The H1 canary (`an_older_format_still_opens_forever` — a forged `format_version: 0` archive
  restores) stays green, untouched.
- **§C parked-not-dead wrappers.** The `api/password.rs` module `#[allow(dead_code)]` (5.6's
  Change-Password UI) + the registered-but-UI-less commands. Each is a wrapper over a *registered,
  tested, working* command whose only absence is a UI — the exact signature 2.10.1 misread. *(The
  spec's §C example list — `api::backup::{inspect,restore}` — was stale: `inspect` carries no allow,
  `restore` does not exist (the verb is `replace`), and the byte-kit commands are kept live via
  `generate_handler!`. The intent held; the plan touched none of them.)*
