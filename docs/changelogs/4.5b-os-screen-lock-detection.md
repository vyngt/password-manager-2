# Slice 4.5b — OS Screen-Lock Detection

Lock the vault when the **workstation** locks. Slice 4.5a moved the auto-lock
timer into the backend and built a hard-TTL reaper + a frontend teardown that
wipes decrypted material from WASM; 4.5b adds a second trigger to that same
machinery — an OS screen-lock — **reusing 4.5a's teardown, error path, and
periodic task verbatim**. Windows-only + a stub (mirroring the biometric infra);
macOS / Linux stay password-only by design. Spec:
`.../Phase 4 - TOTP & Security Hygiene/Specs/4.5b - OS Screen-Lock Detection`.

**One `windows` feature (`Win32_System_RemoteDesktop`), no new crate**, no
migration, no new `AuditAction` (reuses `Locked`), no new frontend code.

## ✅ The flag-semantics gate — smoked on-device, then wired (acceptance criterion #1)

The WTS lock/unlock flag (`WTSINFOEX_LEVEL1.SessionFlags`) is documented as
**possibly inverted on the console session** (reportedly since Windows 7). An
inversion would lock the vault whenever the screen is *un*locked — worse than no
feature at all. So the spec's acceptance criterion #1 required an **on-device Win+L
smoke before the lock sense was trusted** (a human — WebDriver cannot lock a
physical workstation).

**Smoke result (2026-07-12, on the target Windows box):** the raw `SessionFlags`
read **`1` (`WTS_SESSIONSTATE_UNLOCK`) while unlocked** and **`0`
(`WTS_SESSIONSTATE_LOCK`) while locked**, cleanly, across a Win+L / unlock — the
**documented, non-inverted sense**. The console-session inversion did **not**
occur on this machine. `WindowsScreenLockWatcher::is_screen_locked` is therefore
wired to **`Ok(flags == 0)`** (a query failure still returns `Err`, which the
scheduler fails open on; the raw flag is still logged on change for diagnostics).

*Historical note: the stack originally shipped in a fail-safe log-only state
(`is_screen_locked` returning `Ok(false)`, never locking) so the whole slice could
land + verify headlessly while this on-device gate stayed open. The mechanism (edge
detection → reap → WASM wipe) was proven by the memory double + e2e; only the
Windows flag semantics awaited the smoke, which this change closes.*

## What shipped

### Core (`vedge-core`)
- **`application/vault/ports/screen_lock.rs`** (NEW) — `trait ScreenLockWatcher:
  Send + Sync { fn is_supported(&self) -> bool; fn is_screen_locked(&self) ->
  Result<bool, VaultError>; }`. **Query-shaped** (not callback-registration) and
  **synchronous** — mirroring `BiometricAuthenticator`. Registered in `ports.rs`
  after `repository` (alphabetically last).
- **`infrastructure/screen_lock/{windows,stub,memory}.rs` + factory** — copies
  `infrastructure/biometric.rs` **minus crypto** (`platform_screen_lock_watcher()`
  takes no args, so no `needless_pass_by_value` allow). `windows.rs`:
  `WTSQuerySessionInformationW(WTSSessionInfoEx)` → cast to `WTSINFOEXW`, **check
  `Level == 1`** before touching the union, read `SessionFlags`, free via a
  `WtsBuffer` **RAII `Drop` → `WTSFreeMemory`** (a leak here would leak per tick).
  Scoped `#[allow(unsafe_code)]` + `// SAFETY:` blocks + the "cannot be exercised
  headless" note — the Windows Hello adapter's precedent (this is the crate's
  **second** unsafe site; the 2.8 changelog's "exactly one" prose is updated).
  `stub.rs` inert (`is_supported() == false`); `memory.rs` a settable `AtomicBool`
  **plus** an optional sentinel-file lever for the e2e (below).
- **`VaultError::ScreenLockUnavailable`** (unit variant, after `BreachLookup`,
  before the trailing `Storage`). It never actually reaches a command (the
  scheduler is its only caller and fails open); the tauri `From<VaultError>` maps
  it to `Internal` for exhaustiveness.
- **`Cargo.toml`** — `windows` gains `"Win32_System_RemoteDesktop"`. No new crate.

### Shell (`vedge-tauri`)
- **`state.rs`** — `AppState` gains `pub screen_lock: Arc<dyn ScreenLockWatcher>`,
  threaded through all **3** `AppState::new` sites (compose / compose_test_state /
  `test_support`). New `drain_all_sessions` (mirrors `drain_expired_sessions` but
  removes *every* live session — a screen-lock locks all open vaults at once).
- **`scheduler.rs`** — the 4.5a periodic task gains a **second job** on the same
  5 s tick: `poll_screen_lock` locks every open vault on a **`false → true` edge**
  (edge, not level — a screen that stays locked must not re-lock every tick and
  fight a re-unlock). The `Locked`-audit-then-drop body is factored into a shared
  `lock_handles` used by both jobs. **Fails open**: a query `Err` logs and does not
  lock, and does not disturb the edge state. `spawn` widened to carry the watcher;
  wired in `lib.rs .setup`.
- **`setup/services.rs`** — `resolve_screen_lock_watcher()`, the two-gate seam
  mirroring `resolve_breach`: under a debug build **and** a non-empty
  `VEDGE_E2E_SCREEN_LOCK_MEMORY` (a sentinel-file path) it swaps in the memory
  double; otherwise the platform watcher. Neither gate holds in a shipped bundle.

### Tests
- **Core unit** — `stub_watcher_never_locks` (`#[cfg(not(windows))]`);
  `memory_watcher_is_supported_and_settable` + `sentinel_file_drives_lock_state`
  (platform-agnostic).
- **Tauri unit** (`scheduler.rs`) — `memory_watcher_drives_lock` (edge → reap +
  `Locked` audited), `locks_on_edge_not_level` (a persistently-locked screen does
  **not** re-lock; a fresh edge does), `query_failure_fails_open` (an `Err` does
  not lock).
- **e2e `screen_lock_wipes_wasm_plaintext`** (`VEDGE_E2E_SCREEN_LOCK_MEMORY`,
  per-scenario) — seed the generator history → create the sentinel file → assert
  `is_unlocked == false` **AND** the DOM is back at `/` **AND** the history is
  empty on re-unlock.

## Deviations / DRIFT from the spec
- **Step Zero honored literally: log-only first, smoke, then wire.** The spec's
  Step Zero is "write the poll, log the raw flag wired to nothing, smoke, *then*
  wire the sense." Done exactly: the full approach-independent stack + logging poll
  landed first (green headlessly), the on-device Win+L smoke confirmed the
  non-inverted sense (unlocked `1` / locked `0`), and `is_screen_locked` is now
  wired to `Ok(flags == 0)`. Acceptance criterion #1 is met.
- **The e2e lever is a sentinel *file*, not the settable `AtomicBool` the spec
  named.** The e2e runs in a separate process and cannot reach into the app's
  memory to flip a flag; a wall-clock delay (the 4.5a TTL seam's shape) would race
  the setup time. A file the harness creates *after* setup gives a **deterministic**
  `false → true` edge on a live session. The settable `AtomicBool` is retained and
  is what the in-process unit tests use; the memory double simply also honors a
  sentinel path. `VEDGE_E2E_SCREEN_LOCK_MEMORY` carries that path.
- **Concrete periodic task, not a `dyn ScheduledJob` trait** — inherited from
  4.5a's design (a `dyn` async trait needs `async_trait`, not a `vedge-tauri` dep;
  "zero new deps" holds). 4.5b is the second job on that one task, exactly as 4.5a
  anticipated.
- **No Settings toggle.** The spec caps UI at "a single Settings row" and the plan
  omitted one; screen-lock detection is always-on when supported (like the
  always-present breach checker / biometric platform impl). A toggle is a trivial
  follow-up if wanted. No acceptance criterion requires it.

## Self-review outcomes
Four adversarial finder angles (unsafe WTS FFI, scheduler concurrency + edge,
cross-file wiring / error map / e2e, cleanup + altitude + CLAUDE.md). **Verified
clean:** the `WtsBuffer` frees exactly once on every path (incl. the early
returns); the union discriminant (`Level == 1`) is checked before the union read;
null is guarded before the cast; the `StdMutex` is never held across an `.await`
(`drain_all_sessions` fully releases it before `lock_handles` awaits — behaviour
identical to the pre-4.5b inline reaper loop); edge detection never causes a
*spurious* lock and fail-open only ever risks a *missed* lock; all 3
`AppState::new` sites pass `screen_lock` in the right slot; the two-gate seam
can't select the memory double in a release bundle; the e2e asserts the DOM (not
just `is_unlocked`) and the sentinel edge suppresses a re-lock after re-unlock.

**Four fixes applied:**
- **Validate the WTS `BytesReturned` before the cast.** A successful query that
  returned a short/legacy buffer would have been dereferenced as a full
  `WTSINFOEXW` (an OOB read per tick). Now `bytes >= size_of::<WTSINFOEXW>()` gates
  the cast — defensive, since the info class normally fails cleanly when
  unsupported.
- **Wired `is_supported()`.** It was dead API (defined + tested, never called).
  The scheduler now checks it once and **skips the screen-lock sweep entirely off
  the supported platforms** — the stub is truly inert, and the method is
  load-bearing instead of decorative.
- **Removed a misleading `let _ = flags;`** in the Windows adapter — `flags` is
  already consumed by the on-change log, so the discard was a no-op that read as
  dead code inviting a "cleanup" that would break the log.
- **Tightened the module doc** so "returns `Ok(false)`" is scoped to the
  successful-query path (a query failure returns `Err`, which the scheduler fails
  open on) — either way it never locks.

**Accepted (documented design tradeoffs, not fixed):**
- **Sub-`TICK` lock/unlock is unobserved** and **a lock/unlock cycle within one 5 s
  tick is missed** — inherent to polling a level source (bounded by `TICK = 5 s`).
  This is precisely the poll-vs-event tradeoff the spec deliberately chose, with
  `WTSRegisterSessionNotification` documented as the fallback.
- **A query outage spanning a screen unlock+relock can miss the second lock edge**
  (fail-open leaves `prev_locked` unchanged on `Err`). Fixing it (resetting the
  edge on error) would introduce a *spurious* lock when the query recovers — the
  wrong side of the asymmetry. Fail-open deliberately trades a rare missed-lock for
  never ejecting a working user.
- **A poisoned session mutex consumes the edge without locking** — identical to the
  4.5a reaper's behaviour (both use `let Ok(..) else { return }`), and a poisoned
  map breaks the whole session subsystem regardless. Not a 4.5b regression.
- **A vault unlocked *behind* an already-locked screen isn't re-locked until an
  unlock→relock cycle** — unreachable in practice (you cannot drive the app to
  unlock a vault while the workstation is locked). The documented edge-vs-level cost.
- **The memory double carries two levers** (settable `AtomicBool` + sentinel file)
  — not redundant: the `AtomicBool` serves in-process unit tests, the sentinel
  serves the separate-process e2e. Kept as one struct for the single trait impl.
