# 5.3a — Export & the Format (2026-07-16)

The first of slice 5.3's three PRs (5.3a export+format · 5.3b import+preview · 5.3c tweezers+benchmark),
and the one that matters most to get right: **5.3 writes the only permanent artifact in Phase 5.** The
`.vbk` backup was never a real freeze — it tars the already-encrypted `.vdb` and inherits its compatibility
story. **The export file has no parent.** Once one export exists on a user's disk, every future VEdge must
read it — forever.

This PR delivers the encrypted-export format, the plaintext-CSV liberation adapter, and the export UI. Import
(the other half of the round trip) is 5.3b; this PR proves the format at the **format level** so it is not
frozen on faith.

## 🔴 Decision ① — the export DTO is its OWN type

`domain/export/dto.rs` defines `ExportEntry` (9 types + `Unknown`) + `ExportBundle` + `EXPORT_FORMAT_VERSION`,
duplicating the *shape* of the payload structs (`ExportMeta` vs `CommonMeta`, `ExportTotpParams` vs
`TotpParams`, `ExportAddress` vs `Address`) rather than referencing them. The DTO binds **zero** vault schema
— the only external types it touches are `SecretString` (a hygiene wrapper) and `serde_json::Value` (the
opaque carrier for `Unknown`). **The duplication IS the decoupling.** If export re-used `EntryPayload`, every
future change to the at-rest encoding (the JSON→binary decision — see `05 Research/Core Hardening/04`) would
break every export ever written, and that decision would be frozen forever by a *file format*.

The forward mapping `payload_to_export` (`domain/export/mapping.rs`) is the boring, mechanical, per-variant
bridge. **`tests/payload_wire_format.rs` stays green and untouched** — the canary for ①.

## 🔴 Decision ③ — `Unknown` round-trips byte-faithfully

A vault written by a *newer* build holds payloads this one can't parse; they survive at rest as
`EntryPayload::Unknown { unknown_fields }`. Export preserves them verbatim as
`ExportEntry::Unknown { raw: serde_json::Value }`. Skip them and export silently drops the user's data while
promising the opposite. Proven by `unknown_round_trips_byte_faithfully` and the full-envelope round-trip.

## 🔴 Decision ⑥ — the sealed envelope, self-describing, `>` not `!=`

`infrastructure/export/envelope.rs` seals `[magic][format_version][kdf_id][m][t][p][salt][nonce] ‖
XChaCha20-Poly1305(tar)`. The AEAD reuses the vault's own `aead_encrypt`/`aead_decrypt` (now `pub(crate)`) —
no second XChaCha20 path. The key is a **fixed** Argon2id profile (`m=64 MiB, t=3, p=1` — RFC 9106's
memory-constrained second profile, `p=1` because WASM is single-threaded) derived **directly from the
passphrase** (no 2SKD, no Secret Key). The header is self-describing, so a future/weaker build reads the
params from the artifact; the version guard **refuses newer, accepts older, forever** (`>`, against a named
`const`). H1 has shipped twice this phase — pinned by the `refuses_newer_version_accepts_older` canary and a
self-describing-params test (a 19 MiB artifact opens on the 64 MiB build).

## 🔴 Decision ② — no plaintext to disk, ever

Export decrypts everything: the tar inside holds real passwords, keys, card numbers, and document bytes as
plaintext. `infrastructure/export/archive.rs` builds and reads the tar **entirely in RAM** (pre-sized to
avoid realloc-abandoned buffers; returned `Zeroizing`), and the use case (`export_entries`) streams
`DTO → tar → AEAD → file` so **only the sealed ciphertext ever touches disk** — one `fs::write`, no temp
file, not on any path. The 5.2 `write_archive` + `TempDir` staging idiom (correct there, where the payload is
already ciphertext) is disqualified here. Proven at the use-case level: an encrypted export writes **only**
its destination, and the file is opaque.

## 🔒 Decision ⑤ — the frozen CSV adapter

`infrastructure/export/csv.rs` — columns `name,username,password,url,notes,tags`, **logins only, forever**.
`csv` (BurntSushi). We strip the UTF-8 BOM on read (the crate won't); export is UTF-8, no BOM. **Formula
injection: values are never silently mutated** — a password starting `=` round-trips byte-exact, with RFC
4180 quoting and a loud warning; an opt-in *spreadsheet-safe* mode apostrophe-**prefixes** risky cells (never
strips). A short row becomes a positioned `CsvRow` error, not a failed import (the shape 5.3b's preview
badges consume).

## The UI, and the honest warning (⑧)

Settings ▸ **Export** (`features/settings/export_panel.rs`, `api/export.rs`, command `export_entries`,
`ExportReportDto`): choose encrypted (a passphrase; all entry types) or plaintext CSV (logins only), pick a
destination, export. The ⑧ warning is always visible — *a file cannot be reliably wiped from modern drives,
keep exports on an encrypted volume* — and the CSV path carries a second, louder one. VEdge never claims a
plaintext file can be securely deleted.

## Drifts & decisions (from the as-planned spec)

1. **The sealed export is audited as `Exported`, not `BackupCreated`.** `Exported` means readable-or-portable
   data left the trust boundary; `BackupCreated` is reserved for same-disk `.vbk` backups (and must never
   silence "you have never backed up"). Both export formats leave the vault as a portable copy → one
   vault-level `Exported` row.
2. **CSV is a *plaintext liberation* file, distinct from the encrypted envelope.** ② forbids a plaintext
   *temp* on the encrypted path; the CSV is plaintext *by the user's explicit choice* (interop), which is
   exactly why the ⑧ warning and the formula-injection stance matter.
3. **`csv` is the only new dependency in 5.3a.** `url`/`psl` (the spec listed them for the whole slice) are
   for import **duplicate detection** and land in 5.3b, where that code lives. `cargo-deny` accepts `csv`
   (Unlicense/MIT).
4. **No e2e in 5.3a.** The round-trip e2e (`export_then_import_via_ui`) needs import, and a native save dialog
   is not WebDriver-automatable — both land in 5.3b (an `invoke`-driven round trip, per the 5.2.4 precedent).
5. **`ExportMeta` omits `secret_changed_at`** (health-derived, `create_entry`-owned) — a fresh import
   legitimately resets a secret's apparent age.
