# Slice PG.1 — Vault Integrity Matrix (2026-07-20)

The first slice of **Pre-Gate Hardening**. Phase 5's three worst bugs (5.6.0 tags, 5.7 snapshot
manifests, 5.8 history) were the same bug — *operation X left surface Y inconsistent* — and none was
found by a test that existed for the purpose. This slice builds that test: one reusable
`assert_vault_coherent(home, creds, os)` that **opens the vault home FRESH from disk** (new
connection, KEK re-derived from the supplied credentials — never the live session) and asserts the
*whole* vault is internally consistent, called after every mutating-operation integration test.

## The helper — `crates/vedge-core/tests/common/coherence.rs`

- 🔴 **Fresh open, never the live session.** All three historical bugs returned `Ok`, kept the
  session working, and failed only at the *next* unlock/revert — a session-inspecting helper would
  have caught **none**. `assert_vault_coherent` opens `home/vault.vdb` on a new connection, reads
  every raw row, closes the handle (Windows open-file rule), then re-derives `(KEK, verify_hash)`
  from the on-disk config + creds and asserts against *that*. Generalizes `rekey_vault.rs`'s bespoke
  `dump()`/`derive()`.
- **Every failure names the invariant + the offending row/file** — `"invariant 5 (tag-decrypt): tag
  01K… DEK did not unwrap under the current KEK"`, never a bare `assert!(ok)`.
- **`Creds` / `OsState`.** No `Creds` type exists in prod, so the helper defines a test-only one
  (`master_password`, `secret_key`, an optional `recovery_key`). OS-state (`vault_uuid` + keychain)
  is a **separate optional param**: `os = None` runs the pure-disk invariants, skipping the two
  keychain checks — the SPACE tests (open-backup/restore) use a throwaway keychain and pass `None`.
  `Harness::assert_coherent()` is the one-call common case; post-swap/credential callers pass
  explicit new creds.
- **New read-only `all_history()` repo reader.** Invariants #2 (history decrypt) and #10 (orphan
  history — the entries→history cascade is hand-written, no FK) need to see rows an entry-scoped
  `list_history` cannot. Additive; the future user-facing "Verify vault integrity" action needs it too.

## The invariants (13 candidates; 12 checked)

Entry decrypt (incl. trashed) · every history version under the live DEK · every Document blob ·
no orphan blobs · every tag decrypts + **no NULL-`dek_wrapped` tag** (load-bearing since 5.9 retired
`decrypt_legacy_tag`) · `verify_hash` · `recovery_slot` unwraps to the current KEK (full check gated
on the caller supplying the Recovery Key) · every snapshot re-hashes to its manifest + opens under the
current KEK · referential integrity (tag_ids/folder_id/history-orphans) · every audit row parses ·
`commit_counter` ≥ the keychain rollback baseline · credential-age stamps sane.

🔴 **A real finding, applied: invariant #9 (`last_snapshot_at` vs the store) is NOT a clean global
invariant.** Exercising the helper proved neither direction holds: `replace_vault_from_backup` leaves
a pre-replace undo snapshot while restoring the backup's NULL stamp (non-empty + NULL), and retention
can prune a store to empty under a live stamp (empty + Some). The 5.8 re-key bug it was meant to pin
(empty store, stale Some) is asserted at the `rekey_vault` call site instead. A false-positive
invariant is worse than one pinned where it's true — exactly the discipline this slice enforces.

## 🔴 ④ The acceptance is HISTORICAL — the helper catches all three real bugs, watched to fail

A helper that asserts nothing also passes. Each Phase-5 bug was re-introduced on the source (then
reverted), and the wired suite was run to confirm `assert_vault_coherent` FAILS, naming the invariant:

| Re-introduced bug | Fires | Recorded message |
| --- | --- | --- |
| 5.6.0 — skip the tag re-wrap loop in `rewrap_all_deks` | **#5** | `invariant 5 (tag-decrypt): tag 01KXXYB3P5EVYC3AG9P9Z1Y4N6 DEK did not unwrap under the current KEK` |
| 5.7 — drop the `vault_blake3` re-stamp in `rewrap_one` | **#8** | `invariant 8 (snapshot): snapshot 20260719T194215913Z manifest vault_blake3 (97875…) != on-disk hash (15f47…)` |
| 5.8 — skip the history re-encryption in `reencrypt_one_entry` | **#2** | `invariant 2 (history-decrypt): entry 01KXXYFC05N5B7NZB1CQ9A5NA2 history v1 did not decrypt under the live DEK` |

🔴 **Decision ① vindicated by the 5.8 run:** the re-key vehicle's *re-unlock succeeded* (history is
lazy-loaded — a normal unlock never decrypts it), so **only the fresh-open helper caught the stale
history.** A session-based check would have passed. The fresh open is the test.

## Coverage — every mutating use case calls it (enumerated from `use_cases/`)

Wired after the op in ~35 tests across ~22 files: entries (create/update/soft-delete/restore/
hard-delete/move/favorite/sort/tags) · tags (create/rename/delete) · documents (import/hard-delete) ·
history (capture/restore) · maintenance · snapshot/backup/revert · import · biometric enroll ·
create-vault · and the credential/post-swap family (change-password, rotate, recovery-reset, re-key,
recovery-enroll, open-backup, replace-from-backup, unlock-with-secret-key, recover-from-snapshot).
Plus the one read-only cheap assertion (⑤): `get_entry` must not bump `commit_counter`.

Deliberate exclusions, each because the op leaves a state the invariants *correctly* reject (and the
test is about that): `tampered_blob` (corrupts a blob), the `seed_blob` snapshot tests (orphan blobs
with no entry), `set_tags`'s intermediate synthetic ids (asserted only after the clear), and the
legacy-NULL-tag brick test.

## ⑦ Performance (recorded for Gate 1.0 §G)

New `operation_bench.rs` (`mise bench-ops`, `#[ignore]`, `--release`) times the operations a user
waits through at 100 / 1k / 10k entries, plus the worst case — a re-key of a ~384 MB large-blob vault
(`rekey_vault` is `O(total plaintext bytes)`). Numbers on the dev machine:

```
 entries | create_snapshot | rekey_vault      (create/update_entry are single-shot µs, noisy)
 --------+-----------------+------------
     100 |      63 ms       |   0.58 s
   1,000 |      45 ms       |   3.3 s
  10,000 |     184 ms       |  73.2 s

 big-blob re-key: a ~384 MB vault (8 × 48 MiB document blobs) → 3.2 s (119 MB/s)
```

🔴 **The headline finding — re-key's cost is dominated by PER-ENTRY overhead, not plaintext bytes.**
10k small entries take **73 s**, while 384 MB of blobs (8 entries) takes only **3.2 s**. So the
spec's "`O(total plaintext bytes)`" framing is only half the story: for a many-entry vault the fresh
DEK + AES-KW + per-row DB transaction + history re-encrypt + journal overhead (~7 ms/entry) dominates,
and *that* is the worst realistic case, not big blobs. This validates 5.8's determinate progress
`Channel` as necessary (a 73 s operation must not look hung). The gate should re-run on release
hardware and decide whether a batched-transaction re-key is worth it for large vaults.
