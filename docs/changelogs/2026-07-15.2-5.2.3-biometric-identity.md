# 5.2.3 — Biometric Identity & 5.2.x Debt (2026-07-15)

Closes the **5.2.x family**. One real security bug and three deferred promises, gone.

## B1 — 🔴🔴 Biometric was keyed on the file path, not the vault

Since 5.2.0 a vault's identity is its intrinsic `vault_uuid`, and the keychain was re-keyed onto
it — but the Windows Hello port was **missed**. It still hashed `vault_id.path()`. Two
consequences, one of them serious:

- **Convert silently un-enrolled every user.** A different path → a different `SHA-256` → a
  different Hello credential. The next fingerprint prompt just wasn't there, with no explanation.
- 🔴🔴 **The old KeyCredential was stranded in the TPM forever — still holding the vault's KEK.**
  `disable()` computed the *new* name, so nothing could ever reach the old one. A Windows
  credential is addressed only by its name; once the home is renamed the name is gone, and **no
  future version of VEdge could delete it.**

**Fix — mirror the keychain exactly.** The `BiometricAuthenticator` port's four keyed methods now
take `&str` (the uuid), and a fifth — `purge_legacy(&VaultId)` — deletes the legacy path-hashed
credential (keyring blob **and** the TPM KeyCredential). `migrate_vault_layout` calls it
best-effort, after the durable commit, beside `migrate_secret_key`, and **reports** the reset:
`MigrateVaultLayoutOutput.biometric_reset` → the Convert flow shows *"Biometric unlock was turned
off by the upgrade. Re-enable it in Settings."* **Honest beats silent.** It does **not** re-enrol
(that would need a Hello prompt in the middle of a file migration).

**A moved or renamed vault now keeps its Hello enrolment** — 5.2.0's headline *"a moved vault
still unlocks"* is finally fully true. The only surviving `.path()`-keyer is the keychain's
*legacy read-side* (`os.rs:53`), which is correct.

### The lesson (Standards §2)

The 5.2.0 blast-radius table quoted §2's *"4.6a named one config upsert when there were two"* and
then **named one `VaultId`-keyed port when there were two** — it grepped for the *symbol* it knew
(`KeychainProvider`) instead of the *property* (**"what is keyed on `VaultId`?"**). This slice's
own spec-vs-reality scan then found the spec **under-counted again**: three `BiometricAuthenticator`
impls (not two — there's a `stub.rs` for non-Windows), `migrate_vault_layout` threaded **no**
biometric port at all, and `change_password` held a **second** path-keyed enroll. → **When a
type's MEANING changes, grep for every use of the TYPE, not the call sites you already know.**

## B2 — 🟠 The seamless in-place revert (Decision ⑰)

Reverting from `/v/snapshots` used to lock the vault, revert, and eject you to the launch screen —
re-importing 5.2c's auto-lock-and-navigate hack that 5.2.1 deleted for *healthy* vaults. Now the
backend holds the live KEK, drops the session, swaps, and re-opens: **you stay in the vault.**

Because the KEK accessor, `commit_preserving`, and `rename_retrying` are all crate-private, this
had to be a new **core** use case (`revert_to_snapshot_in_session`) — it can't be assembled in the
Tauri layer. It reuses the existing file-op `revert_to_snapshot` wholesale.

- 🔴 **Fall back, never fail (L1).** A stale snapshot whose ⑬ rewrap failed opens only under the
  OLD KEK, so the re-open fails → the outcome is *"reverted, please unlock"* (`NeedsUnlock`),
  **not** *"revert failed"*. The swap already committed.
- ⚠️ **The Windows handle race, a third time** (*"an async close is not a close"*): the use case
  closes the session's DB synchronously (`close_session_db`) before the swap, and the swap already
  uses `rename_retrying` on a blocking thread.
- The **launch-screen** corrupt-vault path (H0) is untouched — it has no live session to preserve
  and keeps the session-less `revert_to_snapshot` command.

### 🔴 The bug the pressure-test caught before any code was written

The first design tore the session down **before** running the revert. But `revert_to_snapshot` has
many *read-only, pre-commit* failure modes (unknown/corrupt/unsupported snapshot). On any of those
the user would have been **ejected and forced to re-authenticate for a non-destructive validation
failure** — strictly worse than today. Fixed: a **read-only preflight** (`verify_snapshot_revertable`)
runs with the session still alive; teardown happens only once committed to the swap. Three honest
outcomes — `Reverted` (stay), `NeedsUnlock` (swap done, re-open failed), `CommitFailed` (torn down
but the swap failed; rare, e.g. a full disk) — the last two navigate to the launch screen.

**Audit fix.** Reusing `unlock_with_kek` would have forged a `BiometricUnlocked` row after every
revert, even on password-only vaults. The reopen goes through a new `unlock_with_kek_quiet` that
suppresses the unlock audit — the honest event is the revert's own `BackupRestored`. **No new
`AuditAction`** → the `ACTION_NAMES` count-tie test is untouched.

**Concurrency.** The command holds the session slot for the whole operation (`get_session`, not
`remove_session`) and replaces the session **in place** (`*guard = session`) on success — no
remove/insert window a concurrent unlock could slip through.

## B3 — 🟡 Picker self-heal

A recents row whose path is gone but whose sibling `<stem>.vedge/` holds a readable `vault.vdb`
(a legacy `.vdb` row after an out-of-app convert, or a vault moved into place) is now silently
re-pointed. `healed_recent_path` is **pure and read-only** — it checks the SQLite header, never
opens a pool, migrates, or WAL-pins (it runs against every recent at startup, the exact reason
5.2.2 rejected the `mode=rw` fallback). Only the app.db row is written; the vault's mtime is
provably unchanged.

## B4 — 🟡 The convert e2e (and the seam it needed)

`open_old_layout_vault_and_convert` runs the real Convert → unlock → decrypt through the UI. It
needs a genuine old-layout vault, which `add_recent_vault` refuses to register — so a debug-only,
`VEDGE_E2E_SEED`-gated command (`e2e_downgrade_to_legacy`) lays a real `.vedge/` home back out as a
legacy `<stem>.vdb` + `<stem>.vedge_blobs/`. Gated exactly like `resolve_keychain`: the enabling
gate is a `cfg`-twin compiled to a constant `false` in release, so **no env var can talk a shipped
app into rearranging vault files.** The keychain is left untouched — Convert preserves the uuid, so
`secret:{uuid}` keeps working and the e2e unlocks with the master password alone. Pinned by a
release-impossibility test.

## Deviations from the spec

1. **B1 unlock ordering → a `read_target_state` uuid probe, not a core unlock refactor.** The spec
   said *"reorder, do not add a read"*; instead `biometric_unlock` / `is_enrolled` / `disable` read
   the plaintext uuid via the **same hardened `mode=ro` probe** the openable badge already uses,
   before the gate call. `target.rs` itself rejected a `mode=rw` fallback with the identical
   reasoning — a read-only probe fits this codebase's caution better than touching the
   security-critical unlock path. It also fails fast on a corrupt vault *before* the Hello prompt.
2. **B4's e2e asserts convert → unlock → decrypt only**, not the biometric-reset-reporting bonus —
   that needs a seeded *legacy* biometric credential in the memory double, too fiddly for headless.
   Host tests #2–#4 + the human smoke cover it.
3. **B2's e2e is the updated `snapshot_and_revert_via_ui` + a focused `revert_stays_in_the_vault`.**
   The old test asserted the *eject* flow, which B2 makes false — so it was rewritten to the
   seamless behavior rather than left to fail.
4. **B1's "moved home" host test asserts the exact KEK roundtrips under the move-invariant uuid**,
   rather than physically renaming a home with an open handle (a Windows hazard). The physical-move
   proof is the on-device human smoke.
