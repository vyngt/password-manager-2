# Slice 4.6a — Core & Scheduler (Debt Paydown, part 1 of 2)

The backend half of the phase's debt slice. Gives a vault an **identity**, makes the
scheduler a real scheduler, and — finally — **runs retention**. The frontend half
(the `try_*` panic sweep, `Select` relocalize, `Pagination` localization) is the
separate slice **4.6b**. Spec:
`.../Phase 4 - TOTP & Security Hygiene/Specs/4.6 - Debt Paydown` (§§A1–A5).

**No new crate.** One additive SQLite column + one migration; a `ScheduledJob` trait
(on the `async-trait` dep 4.4 already added); a reused DTO (`MaintenanceReportDto`
already existed in `vedge-ipc`); one new app `api::` wrapper + a Settings tab.

## A1 — `vault_uuid`: the vault finally has an identity

A vault's only identity was its **file path** (`VaultId(PathBuf)`); moving the `.vdb`
made it "a different vault", hard-blocking LAN Sync (Phase 10) and anonymizing every
Phase-5 backup. 4.6a adds an intrinsic ULID in `vault_config`, **additively**.

- 🔴 **Additive, not a PK swap** — the "clean" option (make the singleton PK *become*
  the uuid) is a corruption trap: `save_config` upserts `ON CONFLICT(id)`, so a new
  key ⇒ no conflict ⇒ a **second** row, and `load_config`'s unfiltered `.one()` would
  then return an arbitrary one (wrong salt on unlock). A nullable column minted on
  create + backfilled on first open is safe with zero special paths.
- 🔴 **The pickup scan found a second upsert the spec missed.** `save_config` is not
  the only `ON CONFLICT(id)` block — **`rewrap_all_deks`** (the change-password path,
  `repository.rs`) has its own hand-built `ActiveModel` + identical `update_columns`.
  `vault_uuid` is threaded through **both** upserts + **both** `ActiveModel`s, or
  change-password would silently drop the identity. Pinned by
  `rewrap_config_upsert_keeps_single_row_and_preserves_uuid`.
- **Mint** in `create_vault` (`Ulid::new()`); **backfill** in `unlock_vault::execute`
  (password) **and `unlock_with_kek`** (biometric — the easy-miss path) via a shared
  `backfill_vault_uuid` helper. `change_password` (clones config) and `recover_vault`
  (delegates to unlock) round-trip the full struct — safe by construction.
- Migration `m20260711_100008_add_vault_uuid` (`ALTER TABLE … ADD COLUMN vault_uuid
  TEXT`, nullable, idempotent). Threaded through the entity `Model`, the domain
  struct, and the mapper (both directions).
- **A copy of a vault is the same vault** (same uuid) — the point, for restore/sync
  coherence. A future "duplicate as a new vault" feature must mint a fresh one; none
  exists (written into the domain doc-comment).

## A5 — `audit_retention_days` divergence resolved

`create_vault` set **365** while the migration default, all fixtures, and doc 20.2 say
**90** — and 4.6a is the slice that makes it observable (it runs `run_maintenance`,
which reads the field). Aligned `create_vault` to **90**; corrected doc
`03 Specs/10 Core/20.2` (the stale "defaults to 365" + "Elixir sidecar runs cleanup"
claims). Pinned by an assertion in `config_fields_are_correct`.

## A2 — `ScheduledJob` reinstated

4.5a dropped the trait believing `async-trait` wasn't a `vedge-tauri` dep; **4.4 had
already added it** (`Cargo.toml:40`). With a third job (maintenance), per-job
intervals, and per-job state all arriving here, the flat 2-job loop no longer scaled.

- `trait ScheduledJob { name; interval; async run(&SchedulerCtx) }` + a narrow
  `SchedulerCtx { sessions, pending_locks }` (**not** `AppState`). Three jobs:
  **TtlReapJob** (per-tick), **ScreenLockJob** (per-tick, Windows-only, owns its edge
  `AtomicBool` — absorbing 4.5b's loop-frame local), **MaintenanceJob** (6 h).
- The 5 s loop accumulates a nominal-tick `since` per job and fires on
  `since >= interval` (pure `tick_due` — testable, wall-clock-independent). A job's
  `run` swallows its own errors, so one faltering never stops the others.
- `spawn` only registers `ScreenLockJob` when `is_supported()` — the stub is inert off
  Windows, so the sweep is genuinely skipped (was a per-tick early-return before).

## A3 — `run_maintenance` wired (three dead jobs, now live)

It was 40 lines of correct, tested, **registered** code that nothing called, so trash
retention, audit retention, and orphaned-blob reaping never ran.

- **MaintenanceJob** runs it over every open vault via **`snapshot_sessions`** — a new
  **non-destructive** accessor. 🔴 The trap: the only pre-existing accessors
  (`drain_all_sessions`, `drain_expired_sessions`) both `remove()`, so cleaning a
  vault through them would **lock it**. `snapshot_sessions` clones the `Arc` handles
  and releases the map lock before any `.await`. Pinned by
  `maintenance_does_not_lock_vaults`.
- **`api::maintenance`** (app) — a thin wrapper over the existing command (DTO reused).
- **Settings → Maintenance tab** — a "Run now" button + last-run counts (trashed /
  audit / orphaned). DRIFT: the "last report" shown is the last *manual* run this
  session; the background 6 h runs only log (no shared last-report state threaded
  through the backend).

## A4 — the `get_session` TTL eviction is now audited

A TTL-expired `get_session` used to `remove()` the slot and return `SessionExpired`
with **no `Locked` row** — a silent lock in a security product's audit trail. The 5 s
reaper usually won the race, but a command inside that window evicted silently.

- `AppState` gains a `pending_locks` queue. `get_session` (sync — can't `append_audit`,
  which is async) parks the evicted handle there instead of dropping it; the scheduler
  drains it through the same `lock_handles` audit-then-drop next tick. Pinned by
  `expired_session_eviction_is_audited`. Lock ordering: `get_session` takes
  `sessions` then `pending_locks` and releases `sessions` first (no cross-path
  inversion).

## Deviations / DRIFT

- **`rewrap_all_deks` second upsert** — added to the spec's blast-radius list (the
  scan found it; §A1 only named `save_config`).
- **The maintenance-panel "last report"** is the last manual run, not the last
  scheduled run (no shared backend state).
- **Concrete periodic task, not per-job async intervals via a runtime timer** — one 5 s
  loop drives all jobs via a nominal-tick accumulator (inherited from 4.5a's shape;
  keeps "zero new deps").

## Self-review (`/code-review high` — 8 angles, 5 finder agents)

**Fixed before the PR:**
- 🔴 **Jobs ran sequentially on one task** — the flagship finding (three finders converged).
  `MaintenanceJob` is the first job to `handle.lock().await` a **live** session and do slow I/O
  (blob walk); a slow or panicking maintenance run would stall or **abort** the loop, taking the
  security-critical reaper + screen-lock down with it (a panic in a job aborts `run_loop`; the
  KEK then stays hot forever). **Fix:** `run_tick` now spawns each due job on its **own task**
  (`tokio::task::spawn`, fire-and-forget; tests await the returned handles) — a slow job can't
  block the others and a panic is isolated to its task. Also moved the per-job `since` accumulator
  into a `Scheduled { job, since }` struct (was a parallel `Vec<Duration>` indexed by position).
- **Softened the maintenance UI copy** — automatic maintenance first fires 6 h after launch, so a
  user who keeps the app open < 6 h relies on "Run now"; the copy no longer claims "every 6 hours"
  unconditionally.
- **Added `ttl_reap_job_locks_and_audits_expired_session`** — direct coverage of the reaper's
  `drain_expired_sessions` branch (the pending-locks branch was already covered).

**Accepted, documented (not fixed):**
- **KEK release on a TTL-expired `get_session` is now ≤ 5 s (scheduler-cadence-bounded), not
  immediate** — identical to the reaper's existing bound for untouched sessions, and the
  per-task-spawn fix keeps the scheduler alive so the queue always drains.
- **A poisoned `pending_locks` drops the evicted handle un-audited** — consistent with the
  codebase's existing poison philosophy (`sessions.lock()` does the same; a poisoned map already
  breaks the session subsystem).
- **`get_session` keeps evicting (A4 queue), not the "leave it for the reaper" alternative** — a
  reviewer proposed not removing the expired slot and letting the reaper drain it (simpler, no
  queue). Kept the spec's explicit queue design; the alternative would change a shipped 4.5a
  `get_session`-evicts contract + test.
- **Maintenance holds a session's mutex for its run** — a brief periodic contention on that vault's
  commands every 6 h; idempotent cleanup, no plaintext leaves the process, and the snapshot keeps
  the vault *unlocked* (the point).
- **The retention 90 change is a real, called-out behavior change** (new vaults; §A5 + the 20.2
  doc correction document it).
