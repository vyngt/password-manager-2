# Slice 5.2c — Rollback baseline + Backup tab

The last of Phase 5's three backup/restore PRs. It folds in **rollback detection**
(Core-Hardening research 06) — restoring an old backup *is* a rollback, and so is an
attacker swapping a live `.vdb` for an older valid snapshot — and ships the clickable
**Settings ▸ Backup** tab that finally makes 5.2a/5.2b reachable by a user. With this,
slice 5.2 (Phase 5's reason for existing) is done.

Spec: `.../Phase 5 - Data Safety & Recovery/Specs/5.2 - Backup & Restore` (P5 rollback
baseline + P7 tab; Decisions ⑤ ⑦).

## What shipped

1. **`commit_counter` column (`m20260713_100009_add_commit_counter`).** Additive
   `INTEGER NOT NULL DEFAULT 0`, mirroring 4.6a's `add_vault_uuid` — existing vaults
   adopt a `0` baseline on migrate. Threaded through the 6 usual sites (entity Model,
   mapper both ways, domain struct, both config ActiveModels) + the 5 `VaultConfig{}`
   construction sites. 🔴 **Kept OUT of both config-upsert `update_columns` lists** so
   an unlock's `save_config` can never clobber the live counter with the stale value it
   read at unlock — the column is advanced ONLY by the bump and restore's re-baseline.

2. **Repo-layer bump (`bump_commit_counter`).** A private generic
   `UPDATE vault_config SET commit_counter = commit_counter + 1` (SQL-side `+1` dodges
   `arithmetic_side_effects`) at the **tail** of the 13 content-mutating writes (12 on
   the bare `self.conn`; `rewrap_all_deks` in its txn — via an explicit in-txn call, NOT
   the ActiveModel, which the omitted `update_columns` would never write). Tail-bump can
   only *under*-count on a crash (a spurious warning at worst), never over-count (which
   would mask a real rollback). Excludes `save_config` / `append_audit` /
   `delete_audit_before` / `update_accessed_at` / `vacuum_into`.

3. **Keychain baseline mirror.** Two **sync** `KeychainProvider` methods keyed on the
   intrinsic **`vault_uuid`** (survives a vault move — the point of 4.6a):
   `read_commit_baseline` (missing entry → `Ok(None)`, a deviation from `read_secret_key`
   so a fresh device is not an error) and `store_commit_baseline`, grown across all **4**
   impls (`os.rs` `counter:{uuid}` account · `memory.rs` second map · the two inline test
   doubles). A corrupt/wrong-length mirror value reads as "no baseline", never a hard
   error.

4. **Non-fatal unlock compare (the safety property).** `rollback_check` runs on both
   unlock paths **after** `backfill_vault_uuid` and reconciles the mirror with one
   asymmetric ladder: keychain error → no warn / never fail; fresh device (`None`) →
   establish baseline, no warn; `file > baseline` → advance the mirror, no warn;
   `file == baseline` → normal; **only `file < baseline` warns** `Some(baseline − file)`
   and leaves the mirror untouched. The result rides a `rollback_warning: Option<i64>`
   field on `VaultSession`; a detected rollback also writes one best-effort
   `RollbackDetected` audit row. 🔴 A missing / broken mirror must never manufacture a
   false alarm, and a rollback check must never fail an unlock.

5. **Surfaced to the UI.** The two unlock commands (`unlock_vault`, `biometric_unlock`)
   now return `UnlockResultDto { rollback_detected, rollback_delta }` (read off the
   session before it moves into the registry, so the use-case return type is unchanged
   and `recover_vault` + test harnesses are untouched). `vault_launch.rs` raises a
   Warning toast on both paths.

6. **`RollbackDetected` audit variant (→20).** Enum + `ALL` + `as_str` + `parse` +
   `vedge_ipc::ACTION_NAMES` (the app filter derives from it — the length tie compiles
   the drift away) + `severity()` (Warning) + `action_label()` + `action_rollback_detected`
   locale (en/vi). The `dto/audit.rs` count-test derives length, so it auto-verifies.

7. **Restore preview + gate + re-baseline.** `BackupManifest` gains
   `#[serde(default)] commit_counter` (populated from the **live** counter at backup
   time — `session.config` is a stale unlock-time snapshot; `format_version` stays 1).
   `target.rs` reads the target's counter via a **separate best-effort sub-query** so an
   un-migrated (pre-5.2c, not-yet-reopened) target can't fail the whole identity read and
   silently disable the uuid-mismatch refusal. `inspect_backup` computes
   `rollback_delta = target_counter − backup_counter` (when the target is ahead).
   `restore_vault` gains a `&dyn KeychainProvider` + `confirm_rollback`: it refuses a
   rollback (`MalformedPayload`) unless confirmed, and after the swap re-bases the mirror
   from the **reopened** config (ground truth), best-effort-after-commit.

8. **Settings ▸ Backup tab (`backup_panel.rs`).** **Back up now…** → save dialog →
   `backup_vault` → Success toast + a last-archive readout. **Restore from backup…** →
   open dialog → `inspect_backup` → a `Dialog` (always mounted, `open=false`) showing the
   diff + a rollback-framing line, or a **blocked** banner (uuid / format / schema
   mismatch → no Restore button). Restore refuses an unlocked target (Decision ⑦), so the
   confirm handler **locks the vault, restores, then navigates to the launch screen** —
   the vault is being replaced anyway. Plain-language framing (Decision ④). Every
   `t_string!` is `untrack`ed; the dialog's interpolated lines use view-context `t!`.

## Decisions honored / drifts from the spec

- **Full rollback detection, surfaced via a session field (not a new `UnlockOutcome`).**
  The unlock-time warning is the actual security value (it's how an attacker's file
  rollback surfaces). Surfacing it through `VaultSession.rollback_warning` kept the
  security-critical use-case return type unchanged — only the two tauri unlock commands'
  DTO changed. *(Spec P5 said "surface a warning on the session"; this is exactly that.)*
- **Manifest gains `commit_counter` (drift).** Spec P1's frozen field list didn't include
  it, but P4/P5 need the backup's counter to compute the rollback delta. Additive +
  `#[serde(default)]`, so `format_version` stays 1 and 5.2a/5.2b archives still
  deserialize. Completes the spec's own intent within its slice.
- **Restore auto-locks (drift).** Spec P7 puts restore in the Backup tab, but Decision ⑦
  refuses an *unlocked* target and the tab is only reachable while unlocked. The confirm
  handler locks first, so a real restore works from the tab; a direct (un-auto-locked)
  restore of an unlocked vault still refuses (the backend guard, e2e-tested).
- **e2e drives backup/restore via `invoke`, not the tab's buttons (drift).** The Back-up
  and Restore buttons open **native** file dialogs a WebDriver can't automate (vault
  creation uses a text field, not a dialog — there is no dialog seam). The two scenarios
  invoke the commands directly while keeping create/unlock/lock/assert UI-driven; the
  clickable tab is covered by manual QA. `restore_refuses_unlocked_vault` tests the
  backend guard directly (the UI auto-locks, so the refusal isn't UI-reachable).
- **Target counter is a separate sub-query** (`read_commit_counter`), not folded into the
  identity SELECT — an un-migrated target lacks the column, and folding it would fail the
  whole read and silently disable the uuid-mismatch refusal.
- **`RollbackDetected` is a 3rd audit variant** beyond Decision ⑤'s two backup ones — the
  spec's "audit it" for a rollback needs one; cheap now that the app filter derives from
  `ACTION_NAMES`.
- **Known gap:** a **recovery** unlock (Emergency Kit) sets the flag + writes the audit
  row but won't toast (the `RecoveryOutcome` DTO carries no rollback field). Deferred.

## Tests

`crates/vedge-core/tests/vault_db.rs` (T1) — every content write bumps by exactly one
(incl. `rewrap_all_deks`); `save_config` / `update_accessed_at` / `append_audit` don't.

`crates/vedge-core/tests/rollback.rs` (NEW, T2) — fresh device / device-behind / genuine
rollback (delta + one `RollbackDetected` row + mirror unchanged) across BOTH unlock
paths; plus the R6 guard: a keychain that errors the baseline read neither warns nor
fails the unlock.

`crates/vedge-core/tests/backup_restore.rs` (+T3, +T4) — the confirm gate refuses an
un-confirmed rollback then re-bases the mirror on confirm (T3); `inspect` reports the
rollback delta against a live ahead target (T4). The 6 existing `restore_vault` call
sites gained the keychain arg + `confirm_rollback`.

`crates/vedge-e2e/tests/backup.rs` (NEW, +2) — `backup_and_restore` (backup → advance →
restore the older backup → the vault reverts to the backed-up state) and
`restore_refuses_unlocked_vault` (restore while unlocked → refused, vault intact).

## Hard gate — handed off

The **kill-mid-restore smoke** (5.2b, Standards §6) now has an ergonomic trigger (the
Backup tab). For each journal state (`Staged` / `VaultAside` / `BlobsAside` / `Swapped`):
start a restore of a large-ish vault → `taskkill /f /im vedge.exe` at that transition →
relaunch → open → assert it opens and `(vault, blobs)` are a consistent pair. Plus a
click-path smoke of the Backup tab itself (backup → corrupt → restore → unlock), since
its native dialogs are not e2e-driven.
