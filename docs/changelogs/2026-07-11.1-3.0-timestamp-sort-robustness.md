# Slice 3.0 — Timestamp Sort Robustness

Make the vault's recency/updated sort correct for **any** valid RFC-3339 timestamp, not just the
fixed-width millis-`Z` form the code assumed, and establish the standing rule *"never compare
timestamps as strings; parse first"* so Phase-10 (LAN Sync) inherits it. Carried Phase-2 debt (review
ticket #5), pulled out of the 3.7 sweep for its hard pre-Phase-10 (LAN Sync) deadline. Spec:
`.../Phase 3 - Password Generator/Specs/3.0 - Timestamp Sort Robustness`.

## The bug

The entry list sorted by comparing timestamp **strings lexically**, relying on an unenforced
invariant that every stamp is fixed-width, zero-padded millis, always `Z`. Lexical and instant order
disagree the moment a non-`Z` / variable-width form appears: `"2026-07-05T12:00:00.000+02:00"`
(10:00 UTC) sorts *after* `"2026-07-05T11:00:00.000Z"` (11:00 UTC) textually, but the `Z` value is
the **later** instant — so descending-recency put the older entry first. Not live today (one
formatter fed the DTOs), but nothing type-enforced it, and a **second, disagreeing formatter already
existed** in core (`to_rfc3339()` → variable-width `+00:00`).

## What shipped

### App — `vedge-app` (the required fix)

- **New `features/vault/timestamps.rs`** — pure `ts_millis(&str) -> i64`: parses RFC-3339 to epoch
  millis (robust to fractional-second width and `Z` vs `+NN:NN`), mapping unparseable/missing →
  `i64::MIN` so a bad stamp sorts oldest deterministically and never panics. Carries the standing
  rule in its module doc: DTO timestamp strings are parsed before comparison; core stays on the
  typed `Timestamp`.
- **`vault_filters.rs`** — `RecentlyUpdated` / `RecentlyUsed` rewritten from lexical `sort_by` to
  `sort_by_cached_key(|e| Reverse(ts_millis(..)))` (parses once per element, stable sort → ties keep
  input order exactly as before). `None`/unparseable → `i64::MIN` → `Reverse` largest → sorts last,
  preserving the old nulls-last semantics. Retired the `cmp_accessed_desc` helper and the now-unused
  `std::cmp::Ordering` import.
- **`recents_filter.rs`** — the vault-picker recency term (`last_opened`) swapped from lexical
  `recency_key: Option<&str>` to `recency_millis: i64` via `ts_millis`; the compound
  exists → recency → name sort is otherwise untouched.
- Replaced both fragile "lexical compare is chronological" comments with the parse rule.

### Core — `vedge-core` + `vedge-ipc` (formatter unification)

Since the app is **pre-release** (no stored data → no migration), the root smell is killed rather
than left latent:

- **New `domain/shared::format_rfc3339_millis(Timestamp) -> String`** — fixed-width, millis-precision
  RFC-3339 UTC (`…000Z`), the single source of truth; re-exported from `domain::shared`.
- Both core SQLite mappers' `ts_to_string` (`sqlite/vault/mappers.rs`, `sqlite/app/mappers.rs`) —
  the single write-path for **every** stored timestamp (entry, tag, audit, entry_history, theme,
  app_setting, recent_vault, known_device, extension_session, vault_config) — repointed from
  variable-width `to_rfc3339()` to the shared helper.
- **`vedge-ipc`** — a test pinning `ts_to_string` to the fixed-width `…000Z` shape (the DTO boundary
  the sort depends on; `vedge-ipc` can't share the core helper — no `vedge-core` dep, must compile to
  wasm — so it stays a separate fn, pinned by test).

This also makes the three DB-level `ORDER BY <timestamp-text> DESC` sites (recents `LastOpened`,
audit `OccurredAt` ×2) correct-by-construction: a SQL `ORDER BY` on a TEXT column is inherently
lexical, so a fixed-width format is the *only* robust guarantee there (short of a schema change). The
recents one is additionally overridden by the app-side `filter_sort_recents` re-sort.

## Deviations

- **Formatter unification included, not deferred** — the spec marked it optional ("nice-to-have if
  cheap"); pre-release status (no data migration) made it cheap and worthwhile, so the root smell was
  fixed now. Recorded in the tracking note.
- **Pre-flight grep finding** — the three DB-level `ORDER BY <ts-text>` sites are lexical-by-nature
  in SQL and are handled by the unification (not parseable in-query without a schema change), not by
  a separate fix. No remaining app-side field `.cmp()` on a timestamp.

## Out of scope (unchanged)

- Ticket #3 (`sort_by_key(name.to_lowercase())` re-alloc) stays in **3.7** — 3.0 introduces the
  `sort_by_cached_key` pattern it will mirror.
- Changing the DTO timestamp representation to numeric/typed — parsing at the compare sites suffices.
- Phase-10 (LAN Sync) conflict resolution — 3.0 only sets the rule it must follow (compare typed
  `Timestamp`, never DTO strings).
