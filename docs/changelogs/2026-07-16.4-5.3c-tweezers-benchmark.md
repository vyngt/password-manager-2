# 5.3c — The Tweezers & the Benchmark (2026-07-16)

The last of slice 5.3's three PRs (5.3a export+format · 5.3b import+preview · **5.3c tweezers+benchmark**).
Two headline deliverables plus a decision recorded with numbers:

1. 🟢 **The tweezers** — recover individual entries *from a local snapshot* into the live vault, without the
   whole-vault sledgehammer of a revert. The highest-value row in the slice.
2. 🔴 **Hard gate 2** — the still-duplicated unlock loop is **folded**, and unlock is **measured at 100/1k/10k**,
   so the 5.5 Encrypted-VaultIndex decision rests on numbers, not vibes.

## 🟢 The tweezers — a snapshot as a third import source

The import preview already takes *rows from somewhere*. 5.3c points it at a snapshot's `vault.vdb`: a new
`begin_snapshot_import(session, snapshot_id)` opens the snapshot with the **current session KEK** (the 5.2.1 ⑬
rewrap keeps every non-stale snapshot's DEKs wrapped under it), maps each entry through the same
`payload_to_export` the export path uses, and stages it into the **exact same** `ImportSession` bundle the
5.3b `commit_import` consumes. Nothing downstream of `Vec<ExportEntry>` changed — the preview, folder remap,
tag match-or-create, and best-effort per-row commit are all reused verbatim. Recovered entries get **fresh
ULIDs + fresh DEKs under the current KEK**: nothing is replaced, no re-key is undone, a wrong pick is one entry.

Because reading a snapshot DB is async and needs the session's KEK — unlike the two byte-sources
(`Encrypted`/`Csv`) which are pure in-memory — the snapshot source is a **separate async entry point**
(`begin_snapshot_import`) rather than an `ImportSource` arm. `commit_import` / `cancel_import` are shared.

**Reading the snapshot without mutating it (Decision 1A).** The snapshot's `vault.vdb` is copied to a
tempdir and the *copy* is opened + migrated (`VaultDbConnection::open` is `mode=rwc` and runs migrations). The
real snapshot is untouched, schema drift across older snapshots is handled for free, and the copy is
*ciphertext* (document blobs live in the shared object pool, not in `vault.vdb`), so no plaintext touches disk
(②). The tempdir auto-deletes.

**Documents recover byte-exact (Decision 2A).** A snapshot's document blobs are not in a `blobs/` dir — they
are in the content-addressed `objects/b3-<hash>.blob` pool, mapped by the manifest's `objects[]`. So a
document's plaintext is resolved `entry_id → blake3 → object_path`, the pooled `[nonce ‖ ciphertext]` is split
and decrypted under the snapshot entry's DEK + `blob_nonce` + `blob_aad`, and staged into `ImportSession.blobs`
exactly as an envelope import stages a tar blob member. `commit_document` then re-encrypts under a fresh DEK.

## 🔴 The stale-snapshot guard — refused, never silent

A snapshot whose ⑬ rewrap failed carries DEKs under an older KEK the current session cannot unwrap; its
`verify_hash_prefix` no longer matches the live vault. `begin_snapshot_import` compares the prefix **first** and
refuses with a new `VaultError::SnapshotStale` (message: *"this snapshot predates a credential change;
recovering from it needs its original password"*) — the launch-screen revert path is the way to open one under
its old credentials. A DEK-unwrap failure that slips past the prefix check is also surfaced as `SnapshotStale`
(belt-and-braces). **Never a silent skip** (spec #15).

## 🔴 Hard gate 2, part A — the folded unlock loop

`unlock_vault.rs` decrypted every tag + entry row into the index **twice**, verbatim, in the password path
(`execute`) and the keyless path (`open_with_kek`) — differing only in the error mapping. Folded into one
private `build_index(repo, kek, remap_err: fn(VaultError) -> VaultError)`: the password path passes
`std::convert::identity` (a decrypt failure there is genuine corruption — the password was already verified),
the keyless path passes `kek_validation_error` (a decrypt failure means a wrong/stale KEK → `WrongCredentials`).
Behaviour-preserving: the existing `unlock_flow` / `biometric` / `rollback` tests are the regression net.

## 🔴 Hard gate 2, part B — the unlock benchmark → the 5.5 decision

New `tests/unlock_bench.rs` (`#[ignore]`d; `mise bench`). 5.3b's import IS the harness — entries are seeded
through the real write path (`begin_import` → `commit_import`). The timed re-open is `unlock_with_kek`, which
takes the pre-derived KEK and **skips Argon2id entirely**, isolating the per-entry loop (AES-KW unwrap +
XChaCha20 open + JSON parse) the VaultIndex blob would eliminate. It also prints the fixed 256 MiB
Argon2id-default cost the loop competes against.

**The numbers (release build, this machine):**

```
Fixed KDF baseline (256 MiB Argon2id-default, one derivation): 921 ms   ← the one-time floor
 entries |  unlock loop | per entry (marginal)
     100  |    23.9 ms  |   ~239 µs   (fixed open/migrate overhead dominates at low n)
   1 000  |    49.1 ms  |    ~49 µs
  10 000  |   268.1 ms  |    ~27 µs
```

(Debug inflates both ~30–60× — the same Argon2id was **29.3 s** in a debug build — so `mise bench`
runs `--release`; a perf number from a debug build would be a fiction.)

**The 5.5 decision — DEFER the Encrypted VaultIndex to Phase 6.** The O(n) loop is a **minority** of unlock
cost at every measured size: ~2.6% of the fixed Argon2id cost at 100 entries, ~5% at 1k, ~29% at 10k. Total
unlock even at **10 000** entries is ~**1.2 s** (921 ms KDF + 268 ms loop). The memory-hard Argon2id KDF is the
floor, and a VaultIndex blob **cannot** reduce it — it would only shave the loop (~268 ms at 10k, ~49 ms at the
realistic 1k). Not worth the write-path complexity + cache-coherence surface now. Phase 6 (Workspaces) names the
VaultIndex a prerequisite anyway, so it lands there naturally, on a real trigger. Numbers recorded in the 5.3
retro and the research note either way.

## The UI — the snapshots page becomes a browser (spec ⑰)

The 5.3b preview table was inline in the import panel; it is extracted into a shared, i18n-free
`ImportPreviewTable(preview, picked, testid)` so the Settings ▸ Import tab and the `/v/snapshots` tweezers
render **identical** rows. The snapshots page gains a **Recover** button per row → an inline preview (the shared
table) → **Recover selected** → the picked entries land in the live vault. A stale snapshot shows the honest
`SnapshotStale` refusal.

Shell: `begin_snapshot_import(vault_path, snapshot_id)` tauri command (mirrors the other snapshot commands —
`resolve_snapshot_dir` + the session guard), `api::snapshot::begin_recover`, `VaultError::SnapshotStale` →
`CommandError::Invalid` carrying the honest message. `commit_import` / `cancel_import` reused unchanged.

## Drifts & decisions (from the as-planned spec)

1. **The snapshot source is a separate `begin_snapshot_import`, not an `ImportSource::Snapshot` arm.** Reading a
   snapshot DB is async and needs the session KEK; forcing `begin_import` (sync, byte-sources) async would
   ripple into every 5.3b caller for no benefit. `commit_import`/`cancel_import` are shared, so the round trip
   is identical.
2. **`SnapshotStale` maps to `CommandError::Invalid`** (carrying the honest message), not a dedicated wire kind —
   consistent with how every other snapshot refusal (5.2.1) collapses to `Invalid` with its message.
3. **The snapshot DB is read via a temp-copy + open-migrate (Decision 1A)**, not an in-place open (which would
   mutate the snapshot like a rewrap does) nor a read-only opener (which would break on schema drift).
4. **The tweezers e2e is `recover_one_entry_from_a_snapshot`** — UI-driven, no native dialog (the first import
   e2e; 5.3a/5.3b deferred theirs because their sources need native file dialogs). It recovers a snapshot's
   entry as a fresh copy (count 1→2) rather than driving a UI delete first, because no per-entry delete testid
   exists on the vault page; the delete-then-recover path is proven at the integration level.
