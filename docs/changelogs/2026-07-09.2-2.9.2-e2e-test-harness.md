# Slice 2.9.2 — E2E Test Harness

Stands up the app's first automated **end-to-end** safety net before the Phase-2 close-out. Every
Phase-2 slice shipped on human `cargo tauri dev` smokes; this drives the **real** binary (frontend →
Tauri commands → `vedge-core` → SQLite) through `tauri-driver` + [`thirtyfour`] (async Rust WebDriver),
automating the accumulated "daily loop" and standing a console-clean guard for the recurring Leptos
reactive-context warning. Opt-in / `#[ignore]`-gated so the default test run stays fast and headless.
Spec: `.../Specs/2.9.2 - E2E Test Harness`.

## Spec-vs-reality corrections (recorded as DRIFT in the tracking note)

- **Determinism seams mostly already existed as production params.** `create_vault` / `unlock_vault`
  both already take `secret_key_b64`; the vault dir is caller-controlled via `vault_path` + the
  `#vault-path` input; document commands take paths. The *only* genuinely missing seam was `app.db`
  isolation → the new `VEDGE_DATA_DIR` env override.
- **The harness self-spawns `tauri-driver`** (RAII `Session`, kills the process tree on drop) rather than
  the spec's "`mise e2e` starts tauri-driver" — cleaner teardown and it lets us pass `VEDGE_DATA_DIR`
  down to the app via the driver child's env. `mise e2e` just builds + runs `cargo test`.
- **UI-drive + real OS keychain**, not the spec's "capture the Secret Key from `create_vault`'s output
  and re-supply it." `create_vault`'s output returns only the `A3-…` *display* string, never base64;
  and create writes the key to the keychain **unconditionally**, so a `secret_key_b64` seed buys nothing
  on the create side. Windows-first, the create wizard writes the key and UI-unlock reads it back
  non-interactively (also what makes the restart test work — Credential Manager persists across the two
  app processes). The `secret_key_b64` override is reserved for keychain-less CI.
- **`tauri_plugin_single_instance` had to be gated.** It is keyed by the app identifier, not the data
  dir, so two instances collide even with distinct `VEDGE_DATA_DIR`s — it would break the restart test.
  Folded into the *same* env seam: skipped when `VEDGE_DATA_DIR` is set (portable/test mode).
- **The build must embed *debug* wasm.** The reactive-context warning is `#[cfg(debug_assertions)]` in
  `reactive_graph`; `cargo tauri build`'s `beforeBuildCommand` forces `--release` wasm and silences the
  guard. So `mise e2e` uses `trunk build` (no `--release`) + `cargo build -p vedge-tauri --features
  custom-protocol` (a plain `cargo build` runs Tauri in dev mode → blank window).
- **Biometric deferred.** The daily loop is password-based, so `platform_authenticator` is left
  untouched; a biometric e2e (via the `Memory` stub) is a future follow-up.

## What shipped

### Production seams (minimal, justified — each generally useful, not e2e-only)

- **`VEDGE_DATA_DIR` override** (`vedge-tauri/src/setup/services.rs`, `resolve_app_dir`): honored *first*,
  before the debug/release branch, so a portable/relocatable data dir (and a per-run temp `app.db` for
  the harness) works in any build.
- **Single-instance gate** (`vedge-tauri/src/lib.rs`): the single-instance plugin is registered only when
  `VEDGE_DATA_DIR` is unset (portable/test instances don't forward-and-exit into an installed one).
- **Console-capture buffer** (`vedge-app/index.html`): a ~10-line `<head>` script wraps
  `console.warn`/`console.error` into a bounded `window.__vedge_warnings` ring, installed before the WASM
  module so boot-time warnings are captured too. Inert in production. The console-clean guard's source.
- **`data-entry-id` on the entry `<tr>`** (`vedge-app/.../vault_table.rs`): a stable per-entry hook so a
  test can address a specific row without matching localized cell text.

### New crate: `crates/vedge-e2e`

- **`src/lib.rs`** — the reusable plumbing: `TestEnv` (temp `VEDGE_DATA_DIR` + vault dir, outlives a
  session for the restart test), `Session` (spawns `tauri-driver` with the inherited env, connects
  `thirtyfour` via the `tauri:options.application` capability, waits for IPC-ready as the positive
  "app actually loaded" assertion, and on drop force-kills the whole process tree — `taskkill /F /T` on
  Windows — so a panic never orphans the driver/app or blocks port 4444), `invoke()` (read-only IPC
  assertions via `window.__TAURI__.core.invoke`), and the **console-clean guard** with a self-test that
  proves it's live (inject a warning → confirm captured → clear).
- **`tests/daily_loop.rs`** — one serial `#[ignore]` scenario: create (UI wizard) → add Login×2 + Note →
  search filters the list → edit → history snapshot captured + panel renders → restore → favorite +
  folder create + move → set theme → lock → **restart** (drop session, relaunch on the same dirs) →
  theme + entries persist → UI-unlock → final console-clean assertion. Mutations go through the UI (so
  Leptos state stays in sync); `invoke()` reads back the assertions.

### Tooling

- **`mise.toml`**: new `e2e` task (trunk debug build → `cargo build --features custom-protocol` → ignored
  test run, serial); `test`/`ci` gates now `--exclude vedge-e2e` so the WebDriver deps aren't compiled on
  every run; `setup` also installs `tauri-driver`.
- **Workspace**: `crates/vedge-e2e` added as a member (deliberately *not* opted into `[lints]
  workspace = true` — it's all unwrap-heavy harness code, mirroring the `vedge-app` precedent).

## Manual boundary (documented, stays human)

Real biometric prompt (Windows Hello / Touch ID — daily loop uses password unlock), native OS file
dialogs (Emergency-Kit save, Document attach/export dialog — the path commands are drivable, the dialogs
are not), and the real OS keychain (used, not mocked; leaves harmless temp-path-keyed residue — see the
crate README for `cmdkey` cleanup). English locale assumed for text/aria selectors; a `data-testid`
sweep is the follow-up hardening.

## Verification

- Gates green: `cargo fmt` (e2e), `cargo clippy -p vedge-tauri --all-targets -- -D warnings` (the two
  seam edits), `cargo clippy -p vedge-app --all-targets --no-deps -- -D warnings` (the `data-entry-id`),
  `cargo check -p vedge-app --target wasm32-unknown-unknown`, and `cargo test --workspace --exclude
  vedge-e2e --lib --bins --tests` → **397 passed, 0 failed** (unchanged — no new host tests; the e2e
  scenario is `#[ignore]`-gated). `cargo check -p vedge-e2e --tests` compiles against `thirtyfour 0.35`.
- **`mise e2e` runs the full daily loop GREEN end-to-end** on Windows 11 / WebView2
  (`test daily_loop ... ok`, ~129 s, mostly Argon2) — create wizard → add ×3 (2 types) → search + clear
  → edit → history snapshot + restore → favorite → folder create + move → theme → lock → **restart** →
  theme + entries persist → UI-unlock, console-clean guard live and clean throughout. Prereqs on the
  runner: `cargo install tauri-driver --locked` + a version-matched `msedgedriver` (Edge/msedgedriver/
  WebView2 all `150.0.4078.48`) on `PATH`. That green daily-loop is what the 2.10 close-out ticks the
  DoD against.
- **Four first-live-run harness fixes** (WebView2 interaction quirks, not app bugs): scripted
  `js_click_aria` for the onboarding acknowledge checkbox (its native `<input>` is `sr-only` →
  WebDriver "not interactable"); clear controlled Leptos inputs by dispatching a real `input` event (a
  bare `clear()` doesn't fire it, so the search filter re-applied its old value); `close_dialog` after
  the version-history modal so it doesn't cover the next step; and **poll** `is_unlocked` after the
  restart-unlock (async Argon2 raced a one-shot assert).
