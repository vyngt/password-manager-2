# 5.2.4 — Delete Vault & Credential Lifecycle (2026-07-15)

Closes the **5.2.x family's last verb.** The family is *the vault as an object on disk*: a folder
(5.2.0) → snapshot it (5.2.1) → move it (5.2.2) → its identity follows it (5.2.3) → **destroy it
(here)**. You could create a vault; now you can delete one — files, all three OS credentials, and
its registry row, in a crash-safe order.

## Step 0 — `recent_vaults` → `VaultRegistry`

The `recent_vaults` table was never a "recently opened" list. It is the authoritative registry
mapping a vault's opaque `vault_uuid` to a home path a human can name — and, as this slice makes
plain, the delete **tombstone**. Renamed end to end (table + domain `RegisteredVault` + port
`VaultRegistry` + `register`/`deregister_vault` verbs + wire DTOs + the 8 Tauri command names and
their `invoke` strings), landed as a self-contained first commit and verified behaviorally a no-op
(735 host tests + 21 e2e green before any feature code). The table rename is one additive
`ALTER TABLE … RENAME TO` migration; the historical migration files are untouched.

## 🔴 The finding: detach leaked three credentials, one of them a KEK

Every vault owns three OS entries keyed on its `vault_uuid`:

```
secret:{uuid}                              ← the Secret Key
counter:{uuid}                             ← the rollback baseline
vedge-biometric-{base64url(sha256(uuid))}  ← a Windows Hello TPM credential — HOLDS THE KEK
```

`recent_vaults` was the **only** thing that mapped that ULID to a nameable vault, and "Remove from
list" dropped the row and nothing else. Delete `work.vedge/` in Explorer and **the KEK outlived the
vault** — a `.vdb` later recovered from disk forensics opens with **no password and no Secret Key**.
That is a residual-risk row [`10.3`](../../03%20Specs/10%20Core/10.3%20-%20Key%20Hierarchy.md) did
not list, created by an operation the user thought was housekeeping. It is B1's root cause for the
**third** time (keychain path-keying → 5.2.0; biometric path-keying → 5.2.3; detach-forgets-the-uuid
→ here): *an identity you cannot resolve is an object you cannot manage.*

## The `delete_vault` core — order is the design

A no-session, no-KEK file operation. The order (Decision ③) is load-bearing and crash-safe:

1. **Resolve the uuid** — the config file is the authority (`record_vault_uuid`'s rule); the registry
   row is the fallback that survives a **corrupt** vault (whose config is unreadable — exactly the
   vault you delete). Then **backfill** the resolved uuid onto the row **before any destruction.**
2. **Delete the home** (`vault.vdb` + `blobs/` + in-home `snapshots/`), retrying the Windows
   lingering-handle window on a blocking thread. **This is the one hard error.**
3. **Delete the three credentials, most-dangerous-first** — the biometric KEK, then the rollback
   baseline, then the Secret Key. Best-effort: a keychain failure sets `credentials_cleaned = false`
   but never fails the (already durable) delete.
4. **Delete the registry row LAST** — the tombstone. Swallowed on error.

### 🔴 The crash-safety keystone (an adversarial-review catch)

The original ordering — resolve `config_uuid.or(row_uuid)`, delete the home, then the credentials —
reintroduced the exact leak on a crash: once the home is gone the config uuid is gone forever, and
`row_uuid` is **often NULL** (a never-unlocked / pre-5.2.2 / corrupt row). A crash in the
home→credentials window would strand all three credentials — the KEK included — **permanently
unaddressable.** Fix: backfill the resolved uuid onto the row *before* the home dies, so the row
that survives a crash still knows the uuid and a re-run (Delete offered again on the now-**missing**
row) finishes the cleanup. Pinned by a direct `resolve_and_backfill` test plus a crash-resume test.

`KeychainProvider` gained `delete_commit_baseline` (idempotent — a missing baseline is `Ok`, unlike
non-idempotent `delete_secret_key`; the delete flow tolerates `KeychainEntryNotFound` as
already-clean, which is what makes the resume idempotent). No audit row: deleting a vault destroys
its `audit_log`; there is nowhere to write and no reader (Decision ⑤).

## The launch-screen redesign (Decision ⑥)

The 288px row had no room for a fifth action, so **every row gave up its buttons.** One `⋯` in the
same place in every state — including the **missing** row, which is the resume surface for a crashed
delete — opens the **vault-details dialog** (the relocated rename, the location, best-effort stats,
a 🟢 **copyable Vault ID** — `mise keychain-audit` keys on uuids and there was no way to see one
without a debugger, and a prose danger zone). "Delete vault…" opens a **second** dialog that
**types-to-confirm the vault name** and states plainly that **`.vbk` backups saved elsewhere
survive.** The hover-pencil rename is gone (invisible until hover, unreachable by touch); the picker
is full-bleed; a long name can no longer blow out a layout (the list truncates with a tooltip, the
unlock panel — which had *no* truncate — now does too, and paths truncate in the **middle** via a
unit-tested `middle_truncate`, never `dir="rtl"`).

## Drifts

- **The core owns the whole orchestration and takes the `VaultRegistry`** (not the spec's 3-arg
  signature). The P0-1 backfill must be durable before the home dies, and the row is the durable
  store — so resolve → backfill → destroy → delete-row is one cohesive, in-`vedge-core`-tested unit.
- **`backup_dir` deletion dropped** (and its test #2). The column is dormant — nothing reads it,
  every write is `None` — so the branch was dead code that could recursively delete an unvalidated
  path. In-home snapshots die with the home; the out-of-home case is a backlog follow-up with a
  containment guard.
- **The command takes `registry_id`**, not the spec's `vault_path`-only signature (path-matching a
  row is fragile).
- **No command-level refuse-unlocked unit test** — the codebase has none (no `mock_builder`/`State`
  harness), so the guard is covered by consistency with `convert`/`replace`/`revert` plus a
  read-only negative `invoke` in the delete e2e.
- **Reveal/Move deliberately out** (⑥e) — recorded in the backlog.
