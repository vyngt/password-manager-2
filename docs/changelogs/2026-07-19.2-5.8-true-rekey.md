# Slice 5.8 — True Re-key (2026-07-19)

**A `change_password` does NOT revoke a captured key.** It rewraps every per-entry DEK from the old KEK to
the new one — but the **DEK bytes and every ciphertext are byte-identical**, only their KEK-wrapping rotates.
So the one attacker a password change cannot stop is the one who **copied the `.vdb` AND opened it once**:
they extracted the DEKs themselves, and those DEKs still open every payload — even entries edited afterward
(an edit re-encrypts under the *same* DEK). A rewrap fixes a *credential-only* leak; it does nothing for
*"a copy of the file left the building."*

This ships **`rekey_vault`** — the only operation that revokes a captured DEK. It mints a **fresh DEK per
entry** and **re-encrypts every ciphertext surface** under new DEKs + a new KEK, so the old DEKs decrypt
nothing that exists going forward. It is `change_password`'s strict **superset** (new KEK, optional new SK,
new `verify_hash`, `recovery_slot` nulled, biometric re-stored — **plus** the DEK rotation), shipped as a
separate **danger-zone** operation, never the default (Decision ⑤: *two operations, labelled by intent* —
"different password" → `change_password`; "my file was copied" → `rekey_vault`).

## The completeness set (spec ① — this phase's signature under-count, pre-empted)

A true re-key is defined by **which ciphertexts get a fresh DEK**. Miss one and that surface still needs the
**old** DEK — so the old DEK is still live and the whole operation is a no-op with a progress bar. The set is
bigger than "entries + blobs":

| Surface | Sealed under | Re-key does |
| --- | --- | --- |
| `entries.ciphertext` (+ nonce) | entry DEK | decrypt(old) → encrypt(new, new nonce) |
| 🔴 **`entry_history.ciphertext` — EVERY version** | the live entry's **stable** DEK (NO per-row `dek_wrapped`) | decrypt(old, version-AAD) → encrypt(new) per version |
| `blobs/{id}.blob` | entry DEK (`blob_aad`) | decrypt(old) → encrypt(new) → **write the new nonce into the payload** |
| `tags.ciphertext` (+ `dek_wrapped`) | per-tag DEK (5.6.0) | mint a **fresh** tag DEK; re-encrypt the name |
| `vault_config.verify_hash` | new KEK | recompute |
| `vault_config.recovery_slot` | — | **NULL** (a KEK change revokes recovery, inherits 5.7 ③) |

🔴 **The landmine — `entry_history` has NO `dek_wrapped`** (it deliberately reuses the live entry's stable
DEK so history survives a password change). The instant a fresh entry DEK is minted, every history version
goes unreadable unless it too is re-encrypted. **The deliverable is a test that makes a partial re-key
detectable**, not a checklist (the 5.4.1 move): the re-encryption loop matches `EntryPayload` with **no `_`
arm** (a future ciphertext-bearing variant *forces* a compile error), and the completeness guard test —
seeding an entry with N history versions + a document blob + a tag — was **watched to FAIL on an entries-only
pass** (history orphaned: `DecryptionFailed`) before it passed.

🟢 AAD is stable (`entry_aad(id, version)`, `blob_aad(id)` bind the id/version, both unchanged), so bindings
survive — only the DEK + nonce rotate, re-encrypted under the **same** AAD. A `Document`'s `blob_nonce` lives
*inside* the encrypted payload and `read_blob` asserts disk-nonce == payload-nonce, so the blob re-encrypt
and the payload patch move in lockstep. `Unknown` (forward-compat) entries re-encrypt their raw bytes
verbatim (a serde round-trip would drop them).

## Crash-safety — stage-and-swap, reuse 5.2's journal (spec ②)

Re-key touches the DB rows **and** external blob files — two storage domains with no shared transaction, so
an in-place mutation has no atomic boundary (**rejected**). Instead it rebuilds the whole home under fresh
DEKs into a staging dir and swaps it in via `journal::commit_preserving` — a crash before the commit point
leaves the live vault untouched (the journal rolls back); only a fully re-encrypted staged home ever swaps
in. Two new journal crash-matrix tests prove the retiring swap (`preserve = &[]`) recovers consistently at
every checkpoint.

The single highest-risk mechanical detail: the live session's open `.vdb` handle must be released **before**
the home rename (Windows won't rename a home holding an open file). The core closes it via the port's
`session.repo.close()` — the exact ordering `revert_to_snapshot_in_session` established (`close_session_db`
then the blocking swap).

## 🔴 Retire old snapshots — a SECURITY requirement, not housekeeping (spec ③)

A pre-re-key snapshot's payloads are still sealed under the **OLD DEKs**, and reverting to it would restore
the exact old-DEK state re-key burned. So `rekey_vault` swaps with `preserve = &[]` — the **one** swap that
does NOT carry `snapshots/` across (the mirror of revert/replace's `&[SNAPSHOTS_DIR]`), retiring every
pre-re-key snapshot. It does **not** call `rewrap_snapshots`. *"A snapshot is what the attacker saw."*

## Locks on success (spec ⑤)

Re-key crosses a credential boundary and rebuilds the whole home, so on success the vault **LOCKS** (the 5.7
revert-locks precedent) and the user re-unlocks against the re-keyed state. The command holds the session
guard for the whole run (so the reaper / screen-lock can't race the swap); on success it `drop(guard)` +
`remove_session`. A **cancel** before the commit point discards staging with the live vault untouched —
signalled by a separate `cancel_rekey` command through an AppState flag on the *outer* lock, so it reaches
the re-key even though the re-key holds the session guard.

## UI — the Settings reorg (spec ⑥)

A new **Credentials** tab holds the five credential *operations* (biometric, change-password, rotate-SK,
recovery-key, emergency-kit), moved out of **Security** (which keeps only behavioural preferences); Re-key
sits in a **danger zone** at the bottom. The dialog is a superset of change-password (current-password reauth
+ new password + `PasswordStrengthMeter` + confirm + an optional "rotate my Secret Key" toggle) with the
honest danger copy (*re-encrypts everything; old copies and backups become unreadable; deletes local
snapshots; cannot un-leak the past*). If the SK is rotated, the show-once new key is displayed before
navigating to the launch screen.

## Progress — streamed over a Tauri `Channel` (the real thing, not polling)

Determinate progress is **pushed**, not polled: `rekey_vault` takes a `tauri::ipc::Channel<RekeyProgressDto>`
param, and the re-key's `on_progress(done, total)` callback `send`s each tick down it as the backend
re-encrypts. The frontend binds Tauri's `Channel` class (`window.__TAURI__.core.Channel`, exposed by
`withGlobalTauri`), attaches an `onmessage` handler that updates a `progress` signal, and threads the channel
into the `invoke` args so Tauri wires it to the command's `on_progress` param. The dialog feeds the
already-existing `vedge-ui` `ProgressBar` (`NN%` + a `done / total` count; a Spinner covers the pre-first-tick
moment). No polling, no second command, no AppState progress cell — the command streams directly, and the
`onmessage` closure is kept alive until `invoke` resolves. (An interim cut used a guard-free-poll workaround;
the Channel is the correct Tauri v2 streaming primitive.)

## The rotated-Secret-Key handoff (a lock-vs-show-once fix)

Re-key can rotate the Secret Key, which is **show-once** — but re-key also **locks** the vault, and the
`AutoLock` watcher polls `is_unlocked` every ~1 s and ejects a locked vault to the launch screen. Showing the
new key on the settings dialog therefore raced the watcher and got cut off before the user could copy it. Fix:
the new key is stashed in a `NewSecretKit` context (provided **above the router**, so it survives the `/v`
unmount) and the dialog navigates to the launch screen **immediately** on success — beating the watcher's poll
(so no misleading "session expired" toast) — where the launch screen shows it in a dismissable modal with no
auto-lock to eject it. The dialog's show-once phase was removed entirely.

## Deviations / deferrals (see the tracking note)

- **Post-re-key baseline snapshot DEFERRED to 5.9.** Re-key retires all local snapshots and leaves zero
  (honest — a fresh start); the optional single fresh baseline was descoped to keep the security core tight.
- Current-password **reauth is required** (re-key is destructive), consistent with change/rotate.

## Tests

- Core (integration): completeness guard (every surface new-DEK-only, old-DEK-nothing) · captured-DEK
  property (old DEKs open nothing current) · snapshots retired · superset (new creds, `recovery_slot` NULL,
  keychain SK) · cancel-before-commit leaves the vault untouched.
- Journal (unit): the retiring swap drops the snapshot store on a full commit AND at every crash checkpoint.
- Wire door (`wire_wasm`): the re-key DTOs carry no DEK / plaintext body / KEK — only credentials in and the
  show-once SK display out.
- `change_password`'s fast rewrap path is unchanged (its KEK-derivation + keychain/biometric tail were
  extracted into a shared `credential_common` module that re-key reuses).
