# Slice 1.6 — Vault Launch, Unlock & Lock

**Scope:** `vedge-app` only. Completes the returning-user entry point; closes the empty-`vault_path` `TODO(UI adaptation)` in `pages/page.rs`.

The `/` screen is now a **launch screen**: it lists recent vaults with on-disk status, unlocks the selected one (Secret Key resolved from the OS keychain by the core), sets the `ActiveVault` context, touches recents, and lands at `/v/vault`. A **Lock** control in the `/v` shell locks the open vault, clears the context, and returns to `/`. **Single-active-vault** model. With this, Phase 1's full daily loop (create → add → list → lock → re-unlock → persisted) is reachable from the UI; only 1.9 (close-out) remains.

## Added / changed

- **`features/vault/vault_launch.rs`** (new) — `VaultLaunch` + `VaultCard`:
  - Loads `api::recent::list_recent_vaults_with_status` on mount. Empty → "Create your first vault" → `/onboarding`.
  - Each recent is a card (name, path, last-opened, status). `exists == false` → "file missing", unlock disabled, **Remove** → `remove_recent_vault` + re-fetch. Selecting a card opens the master-password bar.
  - **Unlock** builds `UnlockVaultInputDto{ vault_path, master_password, secret_key_b64: None }` → `api::vault::unlock`; on Ok `touch_recent_vault_on_unlock`, `active.path.set(Some(path))`, navigate `/v/vault`. Inline error mapping: `WrongCredentials` / `Keychain(..)` (needs Secret Key / Emergency Kit — recover UI is Phase 3) / generic. **No empty-path submit.**
  - **"Open other file…"** via a new `dialog.open` binding → unlock that path; adds it to recents (fresh uuid) on success if not already present.
  - Pure `display_name_from_path` (file stem, strip dir + `.vdb`), host-tested, shared with the create path.
- **`pages/page.rs`** — reduced to a thin `<VaultLaunch/>` wrapper (was the empty-`vault_path` unlock stub).
- **`pages/v/layout.rs`** — added a **Lock** control to the sidebar footer (`FaLockSolid`) → `api::vault::lock` → clear `ActiveVault` → navigate `/`.
- **`features/vault/vault_setup.rs`** — the onboarding create-success path now calls `api::recent::add_recent_vault` (non-fatal), so a newly created vault appears on the launch screen next time. **Nothing wired recents on create before this** — the launch list would otherwise always be empty.
- **`api/tauri.rs` + `api/dialog.rs`** — bound `dialog.open` + `OpenDialogOptions`/`open()` wrapper (only `save` was bound in 1.3). Removed a stale unused `JsValue` import.
- **`locales/{en,vi}/unlock.yaml`** — added launch/unlock/lock keys (both locales); `src/i18n.rs` regenerated.

## Deviations from the spec (see slice tracking note)

1. Inline error line for unlock failures (no `ToastProvider` wired) — consistent with 1.3–1.5.
2. Recents-on-create wired in the frontend onboarding success path (spec cross-check #4 — it wasn't wired anywhere before).
3. `keychain`/wrong-file recovery beyond the inline message is Phase 3 (recover UI). "Missing file" → Remove only.
4. Single-active model (per spec): Lock returns to `/`; no concurrent multi-vault switcher (Phase 2).

## Runtime risk to verify (not covered by host/wasm compile)

`RecentVaultStatusDto` uses `#[serde(flatten)]`; `serde_wasm_bindgen` can mishandle flatten (notably the `sort_order: i32`). The code compiles and the DTO round-trips in serde_json host tests, but the **live** `list_recent_vaults_with_status` decode is only exercised in the running app. **Verify the recents list actually renders in `cargo tauri dev`.** If it fails to deserialize, the contained fix is to de-flatten `RecentVaultStatusDto` in `vedge-ipc` (explicit fields) + update `recent_vault_status_to_dto` in `vedge-tauri`.
