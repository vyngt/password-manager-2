# Slice 3.3 — Generate-into-form + Palette

Make a strong password land in a new/edited entry with **one click**, without a detour to the standalone
`/v/generator` panel. Primary surface: the **Login password field**. Secondary: an expand-to-tune popover
and a command-palette entry point. Almost entirely `vedge-app` wiring over the shipped 3.1 engine + panel,
plus one small shared-preference vertical. **Independent of 3.2** — the fill path writes a signal, never
the clipboard. Spec: `.../Phase 3 - Password Generator/Specs/3.3 - Generate-into-form and Palette`.

## What shipped

### Shared preset — `GeneratorPrefs` in `app_settings`

New `crates/vedge-app/src/features/settings/generator_prefs.rs`, a carbon copy of the `SecurityPrefs`
pattern (keeps `vedge-generator` serde-free — `GeneratorPrefs` is the app-side serde mirror of the engine's
`RandomConfig`): fixed `KEY = "generator.prefs"`, `#[serde(default)]` on every field (an older/partial blob
still loads), `From`/inverse to `RandomConfig`, fire-and-forget `save()`, and a `GeneratorPrefsCtx`
provided + loaded at the app root in `app.rs` (alongside `SecurityPrefs`; **no load gate** — the defaults
are a valid starting preset). App-global, not per-vault. So the inline button, the popover, and the
standalone page all share **one** preset that survives restart.

### `GeneratorPanel` becomes reusable

- New optional `on_use: Option<Callback<String>>` prop. When `Some`, the panel renders a full-width
  **"Use this password"** `Button` that emits the current secret; when `None` (the standalone
  `/v/generator` page) behavior is unchanged (reveal / copy / regenerate only).
- The local `RwSignal<RandomConfig>` is replaced by the shared `GeneratorPrefsCtx` — every engine call
  converts via `RandomConfig::from(prefs.get[_untracked]())`, and each Slider/Toggle edit persists via
  `generator_prefs::save(...)`. The length slider persists on **release** (`on_change_end`), not on every
  drag tick, to avoid write-amplification.

### Login password field — inline generate + caret popover

New `LoginPasswordField` component (`entry_form.rs`, mirroring `SshPrivateKeyField`): the masked `Input`
plus two sibling `IconButton`s —
- a **wand** that fills `data.password` in one click from the last-used preset (synchronous, zero-IPC), and
- a **caret** that toggles a `Popover`-hosted `<GeneratorPanel on_use=…/>`; "Use this password" fills the
  field + closes; outside-click / Escape leaves it unchanged.

The Login match arm now renders `<LoginPasswordField data=data/>` in place of the bare password
`secret_field!`.

### Command-palette action

`ActionId::GeneratePassword` (wand icon), pushed **unconditionally** in `build_rows` beside New-entry /
Lock, dispatched in `run_row` to navigate to `/v/generator`.

New i18n (en + vi): `vault.generate_password`, `vault.generate_tune`, `vault.cmd_generate_password`,
`generator.use_password`.

## Decisions

- **Sibling `IconButton`s, not inside the `Input`** — forced, not chosen: an `Input` with
  `input_type="password"` renders its own reveal eye and **ignores `trailing_icon`**, so the generate
  affordance must be a sibling. No `vedge-ui` change; mirrors the `SshPrivateKeyField` precedent.
- **`GeneratorPanel` reads the shared `GeneratorPrefsCtx`** (rather than keeping a local default only for
  the popover instance) — this is what makes the preset coherent across the inline button, popover, and
  standalone page.
- **Palette rescope** (documented, per Standards §3): the palette action **opens `/v/generator`** rather
  than filling an open form's field. The palette has no unambiguous handle to a specific form's `data`
  signal (it's owned by the form instance, not `VaultUiState`), and reaching into an open form would
  brush against the open low-sev palette bug (Edit no-ops off `/v/vault`, slice 3.7). Inline affordance =
  fill the field; palette = fast access to the generator. Literal palette→form-fill is a noted follow-up.

## Security / memory hygiene

The wand copies the engine's `Zeroizing<String>` into the form's **existing plain `String`** password
field — the pre-existing Phase-2 form model (the password is already plaintext-in-memory while
editing/typing). No new persistence, no new exposure class, no clipboard on the fill path, no secret
logging; the value is encrypted on Save via the normal `create_entry`/`update_entry` path. Tightening the
form model to hold secrets in `Zeroizing` is a memory-hygiene follow-up, not this slice.

## Tests (+4, in `vedge-app`)

`generator_prefs`: `GeneratorPrefs ↔ RandomConfig` round-trip (both `From` directions lossless), `Default`
maps to `RandomConfig::default()`, serde defaults (empty + partial JSON → defaults). Plus the existing
palette `palette_filters_actions_by_query` test extended for the new "Generate password" label.

*(Honest limit: `build_rows` is a component-internal closure — its unconditional placement is covered by
the smoke, not a host test. The form fill / popover / preset persistence UI has no host tests, same as the
3.1 panel.)*

## Verification

- `mise run ci` — fmt-check (rustfmt + leptosfmt), clippy `-D warnings` whole-workspace, test, wasm32 —
  **green**. **484 tests** (was 480; +4).
- An adversarial diff review verified the highest-risk item — `expect_context::<GeneratorPrefsCtx>()`
  resolving inside the `Popover`'s `Portal` — at the source level: `Portal` mounts children under an
  `Owner` that is a **child of the current owner**, and `use_context` walks the owner parent chain (not
  the DOM), so all app-root contexts (`GeneratorPrefsCtx`, `SecurityPrefsCtx`, `ToastProvider`, i18n)
  resolve in both mount sites. It also flagged the slider persisting on every drag tick — **fixed** (now
  `on_change_end`). Reactive-context, refactor correctness, and secret handling all clean.
- **Human GUI smoke (`mise dev`) pending, not blocking:** create a Login → wand fills the password; caret →
  tune (meter updates) → "Use" fills + closes; `/v/generator` still standalone; the preset persists across
  restart; palette "Generate password" opens the generator; console warning-free.

## Out of scope

Other secret types (ApiKey `key`, secret notes) — a `secret_field_with_generate!` macro makes them a fast
follow. Literal palette→open-form fill (deferred rescope). Passphrase / PIN / pronounceable / pattern in
the popover → arrive with **3.4** (the popover hosts whatever `GeneratorPanel` supports). Bulk / history →
**3.5**. Zeroizing the form's `password` field → memory-hygiene follow-up.
