# Slice 5.1 — Recovery & Kit UI

Closes Phase 5's leading DoD item and a **live, shipping dead-end**: the unlock screen
promised *"This vault needs its Secret Key / Emergency Kit"* but gave nowhere to type it.
The `unlock_with_recovery_key` command was implemented, registered, and tested — its
frontend wrapper `api::recovery` had just been deleted by 2.10.1's dead-code sweep (which
can't tell "unused" from "not yet wired"). This slice is **pure frontend wiring**.

Spec: `.../Phase 5 - Data Safety & Recovery/Specs/5.1 - Recovery & Kit UI`.

**Backend delta: ZERO.** No `vedge-core` / `vedge-tauri` / `vedge-ipc` edits; no new
commands, DTOs, migrations, or deps. Host test count is unchanged (**638**) — the
canonical proof that nothing backend-side was touched. All three consumed commands
(`unlock_with_recovery_key`, `write_emergency_kit_pdf`, plus the e2e's read-only
`export_emergency_kit`) already ship and are registered (`vedge-tauri/src/lib.rs:131-134`).

## What shipped

1. **`api/recovery.rs` restored** — the thin wrapper over `unlock_with_recovery_key`,
   mirroring `api/vault.rs::create` (uses `call`, returns `RecoveryOutcomeDto`). Carries a
   do-not-re-sweep doc note; the `api.rs` module-list comment that listed `recovery`
   (and `maintenance`) as "wholly-parked" is corrected — both are now wired.

2. **"Use Emergency Kit…" panel on the unlock screen.** `vault_launch.rs` (orchestrator)
   owns two new signals (`recovery_open`, `recovery_key`) and a `do_recover` handler
   (sibling of `do_unlock`); `vault_unlock_panel.rs` (markup) gains an always-visible
   `Variant::Link` CTA (`data-testid="use-kit"`) under the password form plus a
   `<Show>`-gated panel — a hint, a monospace Secret-Key `<Input id="recovery-key">`, and a
   `Recover & Unlock` button (`data-testid="recovery-submit"`), Enter-to-submit.
   - **Reveal is reactive, no backend probe.** Keychain-missing is only knowable as
     `ApiError::Keychain(_)` from a failed unlock, so the existing arm in `do_unlock`
     additionally opens the panel — the dead-end user lands on the input, next to the toast
     that names the kit. The CTA is *also* always reachable.
   - **The `A3-…` string passes through verbatim (trim only).** `parse_secret_key` (core)
     owns normalization (case, 0/O, 1/I/L) and the checksum; the UI does no re-validation.
   - **Outcome mapping:** `keychain_restored` → Success toast ("Secret Key restored to this
     device"); a partial restore (`keychain_restored == false`) still unlocks and shows a
     Warning with `keychain_error`. Bad key → `ApiError::Invalid` → specific error (the
     parser never echoes input); wrong master password → `ApiError::WrongCredentials`.

3. **"Re-export Emergency Kit" row in Settings → Security.** New `<EmergencyKitSetting/>`
   (modeled on `MaintenancePanel`) mounted after `<BiometricSetting/>`. Reuses the
   onboarding save-dialog flow: `api::dialog::save` → `api::emergency_kit::write_pdf`. The
   `DialogGuard` already suppresses the blur-lock during the native dialog. Keychain-absent
   surfaces the pointed `kit_reexport_no_keychain` message rather than a raw error.

4. **Locales** — 13 keys across `unlock.yaml` (+7) and `settings.yaml` (+6), en + vi.

## Reactive-context discipline (the CLAUDE.md footgun)

Both new handlers read `t_string!` locale strings; reading inside `spawn_local` trips the
reactive-context warning and freezes the value. Every string is hoisted into the handler
body (owner present) before the async block — matching `do_unlock` and `MaintenancePanel`.
The e2e console-clean guard is the backstop.

## Drifts from the spec (spec-vs-reality scan, verified on `develop`)

- **`vault_launch.rs` had only a `show_error` toast helper** — no `show_success`/
  `show_warning`, which the spec's `do_recover` uses. Added both as siblings of
  `show_error` (`ToastVariant::Success`/`Warning`, same `untrack` dismiss-label discipline).
- **`features/settings.rs` is a flat `pub mod`-only module** (no `pub use`) — registered
  `emergency_kit_setting` there and imported the component by full path in `settings.rs`.
- Line-number drift only (spec numbers came from `main`): `<BiometricSetting/>` at
  `settings.rs:251`, the single `ApiError::Keychain(_)` site at `vault_launch.rs:264`,
  the onboarding download flow at `vault_setup.rs:306-347` — all as described.

## Tests

- **e2e (+1 → 12):** `recovery_unlock` in `daily_loop.rs` — create + unlock, capture the
  Secret Key via read-only `invoke("export_emergency_kit")`, lock, then recover from the
  picker (`use-kit` → master password + real key → `recovery-submit` → `assert_unlocked`).
  Negative: relock, flip one base32 data char (2↔3, non-confusable so the core parser can't
  normalize it away), submit, and confirm the vault stays locked. Keychain is intact in the
  scenario — recovery is valid regardless; it parses, unlocks, and rewrites.
- **Host: unchanged at 638** — any drift would signal an accidental backend touch.
